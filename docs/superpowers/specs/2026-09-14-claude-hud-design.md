# claude-hud 方案

> Windows 桌面常驻小挂件，同时显示多个 Claude Code 终端的实时状态。
>
> 状态：**方案待批** · 尚未开工 · 最后更新 2026-09-14

---

## 1. 要解决的问题

用户习惯同时开多个终端跑 Claude Code，以便让 AI 干活时同步处理其他页面。由此产生三个盲区：

1. **哪个跑完了？** —— 得逐个终端切回去看
2. **哪个在等我？** —— 权限请求在某个终端里挂着，不点它就一直卡着，而且你根本不知道
3. **哪个卡住了 / 出错 / 被我打断了？** —— 和"跑得慢"长得一模一样，无法区分

第一轮讨论过"闪 VS Code 任务栏图标"的方案，已否决：多终端场景下闪烁只能告诉你**"有事"**，不能告诉你**"哪个终端、什么事"**。多个终端同时有动静时，闪烁完全失去信息量。

**结论：做一个常驻挂件，一眼扫过就知道每个终端的处境。**

## 2. 已拍板的决策

| 项目 | 决定 | 备注 |
|---|---|---|
| 技术栈 | **Rust + egui/eframe** | 否掉 tauri：为这么小的窗口拖 webview2 + Node 前端不划算 |
| 提醒方式 | **只要挂件，安静模式** | 不闪任务栏、不响铃、不弹系统通知 |
| 点击跳窗口 | **不做** | 技术上最麻烦的一块（VS Code 集成终端无独立 HWND），且非核心诉求 |

| 任务进度 | **智能回退**：有任务清单显示 `3/7`，没有则显示"第 N 步" | 实测当前会话 0 次 TodoWrite，见 §4.2 |

| 完成后留存 | **留着，直到该会话有新一轮活动** | 不自动淡出（便于回来看"哪个跑完了"） |
| 项目位置 | `D:\projects\claude-hud\`（2026-09-17 大搬家后；原 `…\claude\claude-hud\`） | |

### 3.2 可直接借鉴的（已被验证过，不要重写）

1. **事件→状态映射表** —— 含一批踩坑知识（`hoangsonww` 写得最全）
2. **上下文/花费算法：一律不调 API**，读 transcript 的 `usage` 块 × 自建单价表。`hoangsonww` 与 `beyrulibryam` 两套独立实现互相印证
3. **Windows 接线方式**：settings.json 的 `command` **直写 exe 绝对路径**，完全不过 shell（`CC-Hooks-Notifier` 证明）
4. **落盘**：每会话一个 JSON + 原子写 + 轮询，比 SQLite 少一个数量级代码
5. **会话标识用 hook payload 的 `session_id`**
6. **上下文配色阈值**：<50% 正常 / 50–75% 黄 / >75% 红（`claude-context-bar`）
7. **状态集要含"压缩中"**（`gmr/claude-status`）
8. **兜底状态机**：僵尸会话 watchdog 超时（`hoangsonww` / `code-light-ai` 的 5min/30s/60s 规则）

**已被明确否掉的两个做法：**
- `wangjs-jacky` 用 `$PPID` 识别会话 —— macOS 专属且脆弱
- `code-light-ai` 用 `CLAUDE_CODE_SESSION_ID` 环境变量 —— 缺失时兜底成 `"unknown"`，**会把多个会话串成一个**

### 3.3 空位（= 值得做的理由）

> **"Windows 原生 + 多会话并存 + 每会话上下文/花费占比"，三合一，十个项目无一做到。**

- `CC-Hooks-Notifier` 是唯一的 Windows 原生托盘面板，但**没有 session 维度**——所有事件混成一条全局流，看不出"哪个终端在干嘛"，而这正是我们要的
- `hoangsonww` 数据最全，但重心是 Web/Electron 仪表盘，不是一眼扫过的小面板
- `beyrulibryam` 的数据模型最贴合（每会话卡片 + ctx% + 输出 token + 工具数），但只做 macOS

## 4. 关键技术前提（**实测数据，非推测**）

### 4.1 hooks 机制

| 事实 | 影响 |
|---|---|
| 40+ 个事件，含 `SessionStart`/`UserPromptSubmit`/`PreToolUse`/`Notification`/`TaskCreated`/`TaskCompleted`/`Stop`/`StopFailure`/`PreCompact`/`SessionEnd` 等 | 事件粒度足够，无需轮询探测状态 |
| `"async": true` → 后台执行，**不阻塞工具调用**，且不设超时 | 挂点数量不再是延迟约束 |
| `args` 字段 → **exec 形式**，直接 spawn 可执行文件，不过 shell | 启动最快、无引号转义问题 |
| `"shell": "powershell"` 可选 | Windows 下想写 PS 脚本也行 |
| 配置在全局 `~/.claude/settings.json` | **一处配置，所有终端的所有会话生效** |
| 常见输入字段：`session_id`、`transcript_path`、`cwd`、`prompt_id`、`permission_mode`、`effort`、`hook_event_name` | 够用 |

### 4.2 transcript 结构（扫描最近 5 个会话实测）

**行类型分布**：`assistant` 1241 · `user` 580 · `attachment` 562 · `ai-title` 186 · `last-prompt` 171 · `mode` 171 · `permission-mode` 171 · `system` 45 · `file-history-snapshot` 39 · `queue-operation` 20

**内容块**：`tool_use` 532 · `tool_result` 531 · `thinking` 462 · `text` 251

**工具调用分布**（关键）：
```
Bash 204 · Edit 154 · Read 41 · Write 34
playwright MCP 66 · AskUserQuestion 13 · Agent 3 · WebFetch 5
TodoWrite 0    ← 一次都没有
Task      0    ← 一次都没有
```

| 我们需要的能力 | 实测数据源 | 结论 |
|---|---|---|
| 上下文占比 | `message.usage`：`input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens`。实测最后一条 = 146 + 362,880 + 0 ≈ **363K** | ✅ 可行 |
| 会话可读名 | `ai-title` 行（186 条），字段 = `{type, aiTitle, sessionId}` | ✅ 比 cwd 目录名强得多 |
| 当前动作 | `tool_use` 块的 `name` + `input` | ✅ |
| 上一轮耗时 | `type=system` 的 `subtype=turn_duration`（43 条），带 `durationMs` / `messageCount` | ✅ 白捡的 |
| **用户打断** | `type=user` 行上的 **`interruptedMessageId`**（实测 5 次，全部落在 user 行） | ✅ **结构化，不靠字符串匹配** |
| 工具被拒 | `toolDenialKind` = `user-rejected` / `automode-blocked` | ✅ 能区分"你拒的"和"自动模式拦的" |
| API 报错 | `isApiErrorMessage` | ✅ |
| 后台 agent 数 | `pendingBackgroundAgentCount` | ✅ |
| 用户离开 | `system.subtype=away_summary`（9 条） | ✅ 可用作"人不在"信号 |
| **任务进度 3/7** | —— | ❌ **无数据源**（见下） |

**关于"任务 3/7"**：用户选了"智能回退"，但必须记录清楚——**当前工具调用里 TodoWrite 和 Task 各 0 次**，所以这一行现阶段永远会走回退分支显示"第 N 步"。将来若开始用任务清单（`TaskCreated`/`TaskCompleted` 事件，或 transcript 里的 TodoWrite 调用）才会亮。

### 4.3 ⚠️ 上下文上限必须手配（本方案最重要的一条实测结论）

```
转录里记的模型名  = 'deepseek-flash'      （1388 次）
env 里配置的模型名 = 'deepseek-v4.1-flash[1m]'
带 context/window/limit 的字段 = 一个都没有（仅 message.context_management 出现 2 次，与窗口无关）
```

转录**只记 `deepseek-flash`，`[1m]` 后缀根本没进转录**，且全文没有任何窗口大小字段。

**这意味着**：业界通用的"从模型 ID 推断上限"链条（`claude-context-bar` 的权威做法：Haiku/旧版→200K、当前前沿模型→1M、未知或非 Claude ID→兜底 200K）在你的环境里会**把 `deepseek-flash` 判成 200K，导致上下文百分比静默算错 5 倍**。

这种错误最危险：数字看起来完全合理，不会报错，只会让你在错误的时机做决策。

→ **上限必须作为显式配置项，默认 1,000,000，不做任何自动推断。**

## 5. 架构

```
终端1 ┐
终端2 ├─ Claude Code ─┬─ hooks （8 个事件，全部 async）
终端3 ┘               │      ↓ 读 stdin JSON，写状态文件
                      │   %APPDATA%\claude-hud\sessions\<session_id>.json
                      │      （每会话独立文件 + 原子写 tmp→rename，无写竞争）
                      │
                      └─ transcript.jsonl （增量追加）
                             ↓ 挂件按 offset 只读新增字节
                    ┌──────────────────────────┐
                    │  claude-hud.exe  （挂件） │  常驻，无边框+置顶（不透明）
                    │  1Hz 轮询状态文件 + transcript │
                    └──────────────────────────┘
```

### 进程模型：单 exe 双模式

```
claude-hud.exe                     ← 无参数：启动挂件 UI（常驻）
claude-hud.exe --hook <EventName>  ← hook 模式：读 stdin JSON，更新状态文件，退出
```

**为什么合成一个 exe**：hook 模式每次工具调用/事件都要 spawn 一次，Rust 二进制启动约 2–5ms，比 PowerShell（~400ms）或 Python（~150ms）低一到两个数量级；且 exe 绝对路径可直接写进 settings.json 的 `command`，**完全不过 shell**（§3.2 第 3 条）。

### 目录布局

```
D:\projects\claude-hud\
├─ docs\
│  └─ 方案.md            ← 本文档
├─ src\
│  ├─ main.rs            挂件 UI 入口（egui/eframe）
│  ├─ hook.rs            --hook 模式：stdin JSON → 状态文件
│  ├─ state.rs           状态文件读写（原子写、会话索引、僵尸回收）
│  ├─ transcript.rs      增量 tail 解析（offset 记账）
│  ├─ model.rs           状态机（事件 → 状态迁移）
│  └─ ui.rs              渲染层
└─ Cargo.toml
```

**运行时目录（不在项目内）**
```
%APPDATA%\claude-hud\
├─ config.json                 用户配置
└─ sessions\<session_id>.json  每会话状态
```

### 零外部依赖

不调 API、不开端口、不起 HTTP 服务、不写数据库。全部本地文件读写。`beyrulibryam` 那种 WebSocket + 浏览器面板是另一种形态，不是我们要的。

## 6. hook 事件集

注册在全局 `~/.claude/settings.json`，全部 `async: true`：

| 事件 | 用途 |
|---|---|
| `SessionStart` | 会话上线（拿到 `session_id`、`cwd`、`transcript_path`、`source`） |
| `UserPromptSubmit` | → 工作中；顺手记录本轮 prompt 摘要 |
| `Notification` | → 等你确认（`notification_type=permission_prompt`） |
| `PreCompact` / `PostCompact` | → 压缩中 / 清除 |
| `Stop` | → 刚完成 |
| `StopFailure` | → 出错 |
| `SessionEnd` | 会话下线，删除状态文件 |

**不做 per-tool 埋点**（`PreToolUse`/`PostToolUse`）。"当前动作"改由挂件读 transcript 得到——省掉每个工具调用两次进程 spawn，且能顺带拿到工具参数摘要。

## 7. 状态机

| 状态 | 视觉 | 触发信号 | 来源 |
|---|---|---|---|
| 工作中 | 🟢 呼吸 | `UserPromptSubmit` | 调研：**纯文本回复不产生 PreToolUse**，这是"开始工作"的唯一可靠信号 |
| 等你确认 | 🟡 常亮 | `Notification` 且 `notification_type=permission_prompt` | 官方文档 + `hoangsonww` 的正则兜底经验 |
| 压缩中 | 🔵 常亮 | `PreCompact` → `PostCompact` 清除 | 抄 `gmr/claude-status` 的状态集 |
| 刚完成 | 🔵 常亮 | `Stop` | 官方文档 |
| 出错 | 🔴 常亮 | `StopFailure`（会话级）+ transcript 的 `isApiErrorMessage` | 官方文档 + 实测字段。**不注册 `PostToolUseFailure`**——它属 per-tool 埋点，与 §6 原则冲突；工具级失败已能从 transcript 的 `isApiErrorMessage` / `toolDenialKind` 读到 |
| **被打断** | ⚪ 带标记 | transcript 中 `user` 行的 **`interruptedMessageId`** | **本方案实测发现** |
| 待命 | ⚪ 暗 | `Stop` 后超过 `idle_after_sec`（默认 **300 秒**）无新事件 | 兜底。注意：变"待命"只改变**视觉**，会话**仍留在列表里**（§2 决策），直到有新一轮活动 |
| 已退出 | ⚪ 灰 | **由挂件判定** `claude_pid` 不存活（**不是 hook 事件** —— 宿主都死了，不会再有任何 hook 事件） | 僵尸回收，见坑 2 |

### 三个必须处理的坑

1. **Esc 打断不触发任何 hook**（`hoangsonww` 踩过）。若不处理，被你打断的会话会**永远卡在"工作中"**，挂件直接失去可信度。
   → 解法：挂件扫 transcript 中 `user` 行的 `interruptedMessageId`。**实测优于字符串匹配**（文本 `[Request interrupted by user]` 出现 11 次，比结构化的 5 次多，说明字符串会出现在别处，容易误判）。

2. **僵尸会话**：进程被 kill、终端被关，`SessionEnd` 不一定触发。
   → **已实现（2026-09-15）**，做法与初版设想一致：hook 在 `SessionStart` 记下 Claude Code
   宿主的 pid（`SessionState.claude_pid`），挂件每轮判它还在不在。

   **9b 的实测结论**（判据："父进程链能不能**稳定**指到 Claude Code 宿主"）：

   - hook 的 **hop 1 就是 `claude.exe`** —— 注册是 exec 形式、不过 shell，没有中间层。
   - **宿主 pid 对同一个 `session_id` 恒定**（一个会话 3/3、另一个 2/2）。

   ⇒ **能**，故保留 `claude_pid`、走**真实存活检测**，**不**引入超时回收旋钮。

   > 取证过程纠正过一次误判：先拿到的两份样本宿主 pid 不同，一度像是"宿主会变"；
   > 补上 `session_id` 才看出那两份本来就来自**不同会话**（本机同时开着 3 个）。
   > **手边一次观测不能当结论。**

   **三处实现选择，各有理由：**

   | 选择 | 理由 |
   |---|---|
   | `claude_pid` **只在 `SessionStart` 抓** | `snapshot()` 枚举整个进程表实测 **7.5 ms**（release 与 debug 几乎一样 ⇒ 是内核枚举的代价）；hook 本来约 2 ms，放进每个事件会让它慢 4~5 倍。宿主 pid 既然恒定，抓一次就够。`SessionStart` 在新开与 resume 时都触发，能覆盖"同一个 session_id 换了宿主进程"。 |
   | 判存活用 `OpenProcess` + `QueryFullProcessImageNameW`，**不枚举全表** | 微秒级 vs 7.5 ms；挂件每轮每会话各一次，代价可忽略。 |
   | **判不准时一律判"还活着"** | 误判成"已退出"的后果是把这个会话从界面上抹掉，而这是个帮人看"谁还在跑"的工具 —— **最糟的错法就是让活着的会话消失**。`claude_pid` 为 `null` 时**完全不判定**（老状态文件、`SessionStart` 没抓到都走这条）。**宁可漏报僵尸，不可误杀活人。** |

   **"已退出"不是 hook 产生的状态**，而是**挂件推导的显示覆盖**：宿主都死了，不会再有
   任何 hook 事件，"最后一个事件报的状态"会永远停在那里 —— 所以由挂件在渲染时**取代**状态词。

   表现（用户 2026-09-15 裁定）：**先标"已退出"（灰色），连续两轮确认后再移除那一行**；
   僵尸行同时沉到列表最后。

   > ⚠️ **两处已知限制，都落在"漏报"一侧，是刻意的取舍**：① 改造前就已开着的会话没有
   > `claude_pid`，要等它重启（`SessionStart`）才纳入判定；② pid 被**另一个同名
   > `claude.exe`** 复用时会漏报（当成还活着）。

   > ⚠️ 实现期由**反向对照测试**抓到一条会线上发病的 bug：Claude Code 升级时会把**自己的
   > 可执行文件改名**成 `claude.exe.old.<时间戳>`，于是 `QueryFullProcessImageNameW` 给出的
   > basename 不再是 `claude.exe`，而 Toolhelp 的 `szExeFile` 仍报原名 —— 按"取 basename
   > 再判相等"实现时，**本机 3 个真在跑的 `claude.exe` 全被判成"已退出"**，症状是挂件里的
   > 会话一个个莫名消失、且不报错。已改为"相等，或以 `claude.exe.` 开头"。

3. **`SubagentStop` 不能清 waiting**（`hoangsonww` 的 issue）。

## 8. 数据模型

### 状态文件 `%APPDATA%\claude-hud\sessions\<session_id>.json`

```jsonc
{
  "session_id": "7c1e4a90-...",
  "cwd": "D:\\projects\\doc-tasks",   // 取自 hook payload，不从目录名反推（见 §11）
  "transcript_path": "C:\\Users\\user\\.claude\\projects\\...\\xxx.jsonl",
  "display_name": "示例项目报告排版修复",     // ai-title 优先，退回 cwd 目录名
  "claude_pid": 12345,                       // 用于僵尸检测
  "nested": false,                           // 2026-09-18 新增：是不是被另一个会话拉起的子会话（见下）
  "state": "working",                        // working|waiting|compacting|done|error|interrupted|idle
  "state_since": 1757831234,                 // 状态起始时间戳（算计时用）
  "last_event": "UserPromptSubmit",
  "last_event_at": 1757831234,
  "last_assistant_message": "已修复排版，共 12 处",   // 来自 Stop 事件，完成时显示
  "notification_message": "Claude needs your permission",  // 来自 Notification 事件的 message
  "transcript_offset": 524288                // 已读到的字节位置，增量解析用
}
```

### 9.-1 排序：谁排在前面（用户 2026-09-17 裁定）

| 组 | 状态 | 组内顺序 |
|---|---|---|
| **1（最高）** | **出错 / 网络问题**（`Error`） | 越久越靠前 |
| **2** | **完成组**：`完成` · `被打断` · `待命` | 越久越靠前 |
| **3** | **待办** = `等待确认`（`Waiting`） | 越久越靠前 |
| **4（最低）** | **工作中** · `压缩中` | **工作时间越长越靠前** |
| 末尾 | **已退出**（宿主进程没了） | —— |

**一句话**：**先按状态分组（错误 > 完成 > 待办 > 工作中），组内一律"越久越靠前"**，
末尾永远是宿主已退出的僵尸会话。

**"越久"的判据是"进入当前状态多久"**（`Row::elapsed_secs`），**不是**"最近有没有活动"
—— 这是与首版的一处**语义改动**，两者在本机常常同向但会给出相反结果：
一条"已经干了 40 分钟、2 秒前刚有工具活动"的会话，按旧口径（最近活动优先）排最后，
按新口径排最前。用户要的是后者。

> ⚠️ 这与 2026-09-14 的首版**正好相反**（那版：`等待确认` 第 0、`出错` 第 1、
> `工作中` 第 2、`完成/被打断` 第 4、`待命` 第 5）。**改的是"谁更该被先看见"，不是修 bug** ——
> 见到旧顺序的代码注释/文档时不要以为是实现错了。
> 聚合（折叠胶囊用）与列表排序**共用同一个 `priority`**，所以两者一起变。

### 9.0 行首色块 = **会话颜色**（用户 2026-09-16 两次裁定）

用户原话：先是"**色条区别度不高，每个会话一个颜色**"，看过之后又："**不明显，就用红黄蓝绿**、
**色块稍微大一点**"。三件事都落了地：

| 项 | 结果 |
|---|---|
| 谁上色 | **色块答"这是哪条会话"**（`assign_colors`）；**状态词答"它怎么了"**（仍按状态着色） |
| 画法 | **矩形**（`BAR_WIDTH` 8 × `BAR_HEIGHT` 20，圆角 1pt），**不是**原来的 `▍` 字形 |
| 色板 | **红 `#b31f1f` · 金 `#a16207` · 蓝 `#1565c0` · 绿 `#0f6b2e`** —— **只有这 4 个** |

> 色板从 6 收到 4 的原因：用户原话就是"**就用红黄蓝绿**"；而且实测（截图取样）原来的第 6 色
> 石板蓝 `#3d4b6b` 在 8×20 的小色块上与蓝 `#1565c0` **几乎分不出来**。
> **4 正好等于用户声明的上限**（"我最多开四个"），于是"同时可见的互不同色"在他的用法下永远成立；
> 超过 4 条从头上重复。

**为什么改成矩形**：原来那根条是字体里的半块字符（U+258D）。想放大就受两样掣肘 ——
字号一大，行高（= 该行最高字块的 max）跟着涨，**四段纵向间距全要重标**；
而且它**依赖中文字体提供这个字形**。矩形由两个常量说了算，与字体、行高都解耦。

**颜色分配的三条性质**（都在测试里钉着，缺一条用户就会看出来）：
1. **同时可见的会话互不同色**（≤ 色板长度 4）；
2. **与在列表里的位置无关** —— 逐行贪心做不到（换个顺序先来的那条就把色占了），
   所以**先按 `(哈希色, session_id)` 排序再分配**，最后按原顺序放回；
3. **会话集合不变时颜色不变**（哈希色优先，且排序是确定性的）。

> ⚠️ **"黄"只能是深金**：亮黄在白底的对比度只有 **1.1:1**，怎么调都过不了 AA，
> 取 `#a16207`（4.92:1）—— 这些色相里最接近"黄"又满足对比度的那个。
> ⚠️ **这四支色相与状态色重合**（红=出错 / 金=等待确认 / 蓝=完成 / 绿=工作中）。
> 这是"明显优先"的取舍：**色块只表示身份，状态由状态词的颜色与文字表示**。
> ⚠️ **分配的"作用域"是"这一屏画得下的那几条"**（2026-09-17 修）：对着**整份列表**分配时，
> 列表里超过色板长度就从头上重复 —— 而重复的那两个可能**恰好都在可见范围内**。
> 判"画得下几条"要按 **`one_row_h + ROW_BOTTOM_GAP + EXTRA_ROW_GAP`**（相邻两条的**前进量**）
> 算，不是 `one_row_h`：第一版少算了行距，算出"装 7 条"、实际只画 4 条，于是照样撞色。
> 超过色板长度时颜色会重复（已知代价，测试里明写了）。

### 9.1 token 用量与子代理连线（用户 2026-09-16 需求）

```
                     └────┤             ← 有子代理时：一条直角折线指向它
```

- **顶栏**：`全部 N` = 全机今日总量。**账本还没扫过时不写这个数**（写 `全部 0` 等于把
  "还不知道"说成"今天没用"）。
- **行尾**：`N` = **该会话自己**的今日量，**不是**"它所属项目"的 —— 实测 **79/163 份转录跨多个
  `cwd`**（最多 13 个），"所属项目"没有唯一解。项目维度的数照常算（`Ledger::by_project`），只是
  还没有放它的位置。
- **格式**：K/M 缩写（`12.8M` / `980.0K` / `0`），四舍五入会撞到 `1000.0K` 时进位到 `M`。
- **折线**：从「状态词」的**水平中点**垂下、到第二行中心高度**右拐**，停在「子代理 N」左缘外 2pt。
  颜色取状态色。**触发条件：只要有子代理在跑就画**（用户裁定）—— 不是"只在该会话因为子代理而
  显示工作中时才画"，后者会让折线在主代理自己也开始干活时忽隐忽现。
- ⚠️ **token 数字放在第二行、字号与 `上下文 N%` 相同**，两条都是**量出来才定的**：
  放第一行会把会名挤没（最坏情况 160~240pt 会名整个消失、默认 320pt 只剩 3 字）；
  字号用 15pt 会让第二行行高从 8pt 涨到 16pt，连带要重标 `ROW_LINE_GAP`/`ROW_BOTTOM_GAP`/
  `EXTRA_ROW_GAP`（实测 14→18、58→62）且每会话变高、窗口装得下的会话数变少。

**口径（数字为什么是这么算的）**——权威实现在 `src/usage.rs` 的模块头，三条硬要求：

1. **四桶平铺相加**（`input`+`output`+`cache_read`+`cache_creation`）。≈99.8% 来自 `cache_read`
   —— 这个数在量"同一段上下文被重复读了多少遍"，用户 2026-09-14 明确知情并接受。
   **桶会缺**：全机 42,710 行 assistant 里 **12.9% 只有 `input`/`output`**（历史版本无 cache 键，不是 0）。
2. **按行内 `timestamp` 判"今天"**（本地日界，不是文件 mtime，也不是 UTC 日界）。
3. ⭐ **按 `message.id` 归组，组内只算一行**：一次 API 响应会写成多行（`thinking`/`text`/`tool_use`），
   **每行 uuid 不同**、`message.id` 相同、`usage` 基本相同。今天 2245 行只对应 965 个 `message.id`，
   按行累加 **403.2M**、按组取一行 **175.8M** —— **虚高 2.29 倍**，`uuid` 去重救不了。
   组内取 `timestamp` 最大的一行（实测 19,799 组里最后一行的 `output_tokens` 100% 是组内最大值）。

**性能**：`mtime` 预筛（今天没被写过的文件不可能含今天的行）+ 按 offset 增量。
实测启动扫描从 163 份 / 325MB 降到 **3 份 / 8.2MB**。

> ### ⚠️ 2026-09-17：缩放改成了**自己做**（`BeginResize` 在无边框窗口上不生效）
>
> 用户连着两次报"不能缩放"：先是"不能随意调整大小"，修掉死区之后仍"还是不能正常缩放，
> **鼠标放到边缘，光标没有变成可拖动的光标**"。

> **两层原因**：
> 1. 可交互区与缩放判定都挂在**面板内容区**（比窗口小 8pt）⇒ 距窗口边 0~8pt 的那一圈
>    按下**毫无反应**（`ui.interact` 的矩形不含它）。而人抓边框手就是往最边上放的
>    —— 黑边去掉之后更会如此。修法：`window_rect()` = 内容区外扩一个内边距。
> 2. 判定对了之后发的 `ViewportCommand::BeginResize` **也不生效**：它落到 winit 的
>    `drag_resize_window` → `WM_NCLBUTTONDOWN(HT*)`，**把控制权交给系统自己的缩放循环**，
>    而那个循环靠窗口的"**非客户区**"判可缩放性 —— 无边框窗口正是把非客户区去掉换来的。

> 发 `OuterPosition` + `InnerSize`；夹住最小尺寸时把**被拖的那条边顶回去**（否则会一边缩一边飘）。
> 指针必须按**屏幕坐标**记账 —— 缩放会移动窗口（拖左边时原点跟着走），窗口内坐标会跳。

> **光标**：贴边悬停时 `set_cursor_icon` 换成对应的缩放光标（横/竖/两个斜向）。
> ✅ **2026-09-17 用户实机验收通过**（回话「好了」）—— 这是本轮唯一只能由人确认的一环。
> 无边框窗口**没有系统给的那一份**，不自己设就永远是箭头 —— 用户就是这么发现"没生效"的。

> 被它截走。想让一段文字**避开**数码体，唯一的办法是给它一条**不含子集**的族。
>
> ⚠️ **连截断额度也得按那条族算**：数码数字比雅黑宽 **39%**（同字号实测 10.608 vs 7.62pt），
> 拿数码宽度算额度会**过早截断**（名字白少显示几个字，看起来只是"短一点"，不像故障）。
> `text_width_in` 就是为此存在的。
>
> ⚠️ **顶栏族之所以有效，靠的是"顺序"而不只是"缺席"**：微软雅黑**自带数字**，所以 CJK
> 排在族首就已经把 `3` 接走了。变异测试验过：把一个**仍在 CJK 之后**的数码子集塞回去，
> **行为完全不变、测试照样绿** —— 那不是测试无效，是**变异无效**。真正能改变行为的变异是
> "把子集插到 CJK **之前**"，那个当场就红。
>
> **子集是派生字体**：SIL OFL 条件 3 禁止派生版本沿用保留字体名 "DSEG"，故改名
> `claude-hud-digits`；改了什么、授权如何随附、怎么从原版重放，全在
> `assets/claude-hud-digits-NOTICE.txt`。子集是**一次性离线产物**（fontTools），
> **cargo 构建不依赖 Python**。
