# 下载者兼容性检查（2026-10-30）

检查对象：GitHub Releases 上**当前可下载**的 v1.0.1（`claude-hud.exe` 与
`claude-hud-v1.0.1-windows-x64.zip`）。检查的是"别人下载后能不能直接跑、要不要配环境、
在哪些机器上会坏"，不是本机开发环境。

## 一、结论

| 环境 | 结论 |
|---|---|
| **Windows 10 / 11 · x64** | **可用**。解压 → `--install-hooks` → 双击；不需要 Rust、VC++ 运行库、.NET、Node |
| Windows 8 / 8.1 · x64 | 加载层面可启动（依赖的 DLL 在 Win8 已有），但 wgpu 的首选 DX12 后端不可用，**未测试、不保证** |
| Windows 7 | **不能启动**：exe 静态导入 `bcryptprimitives.dll` 与 `api-ms-win-core-synch-l1-2-0.dll`，两者都是 Windows 8 才有的 |
| 32 位 Windows | **不能**：PE32+ / x86-64 |
| Windows 11 ARM64 | 可走 x64 模拟，**未测试**；wgpu 在模拟层的表现未知 |
| macOS / Linux / WSL | **没有对应构建**；WSL 里的 Claude Code 会话也读不到（见 §四.6） |
| Wine / Proton | 未测试；依赖 Win32 + DX12，不保证 |

> 建议 README 与 Release 正文直接写死：**Windows 10/11 x64**。现在的文字只说了
> "仅 Windows"，没有区分版本与架构。

## 二、"下载即用"逐项核对（已实测）

下载了 GitHub 上的两个 asset 并核对：

| 项 | 结果 |
|---|---|
| `claude-hud.exe` SHA256 | `04cb7167…10e779`，**与 Release 正文一致** |
| zip SHA256 | `2b245e7d…e455a3`，**与 Release 正文一致** |
| zip 内容 | `claude-hud.exe` + `README.md` + `LICENSE`，3 个文件 |
| C 运行库 | **静态链接**：导入表无 `VCRUNTIME140.dll` / `MSVCP140.dll` |
| 其他依赖 | 只有 Windows 系统 DLL（kernel32/user32/gdi32/opengl32/dxgi/dwmapi/…） |
| 数字签名 | **NotSigned**（未签名） |
| 需要管理员权限 | **不需要**：hook 写 `%USERPROFILE%\.claude\settings.json`，配置写 `%APPDATA%` |
| 需要装 Python/Node/Rust | **不需要** |
| 启动失败可见 | 是：GUI 子系统无控制台，但启动失败 / 崩溃 / hook 注册失败都会弹系统对话框 |
| 中文字体缺失可见 | 是：窗口出现前弹框说明"中文会显示成方框" |

**结论**：在 Windows 10/11 x64 上，**文件层面确实"解压即用"**；但"直接双击"只能启动挂件，
要看到会话数据还必须先跑一次 `claude-hud.exe --install-hooks`（README 已写）。

## 三、会拦住下载者的三个环境问题

### 1. 未签名 → SmartScreen 警告（每次新下载都会遇到）

`Get-AuthenticodeSignature` 对下载到的 exe 返回 **NotSigned**。从浏览器下载的文件带
Mark-of-the-Web，双击时 Windows 10/11 的 SmartScreen 会先拦一次
"Windows 已保护你的电脑"，必须点"更多信息 → 仍要运行"。企业策略较严的机器可能直接禁止。
这不是 bug，但会让人以为"软件有问题"。

- 缓解：Release 正文与 README 明写这一句 + 给出 SHA256（已有 SHA256）。
- 根治：代码签名证书（有成本），或至少发布一个稳定的下载渠道。

### 2. `context_limit` 默认 1,000,000，对多数人**偏大**

配置默认值是按本项目作者的 1M 上下文模型定的。一个用标准 200K 上下文的下载者不改配置时，
"上下文 N%" 会是真实值的 1/5 —— **数字看起来完全合理，不会报错**，正是项目最忌讳的
"静默算错"。README 已写"必须手配"，但下载者很容易跳过。

- 建议：README 首屏加一句症状说明（"如果你的模型不是 1M 上下文，百分比会偏小，改
  `context_limit` 后重启"）；或在首次运行的对话框里提示一次。

### 3. 没有开机自启；重复双击会开出两个挂件

M5 的"打包 / 路径固定 / 开机自启"一直没做（用户此前裁定 1.0 之前不做）。下载者需要
每次开机手动启动；双击两次会得到两个相同窗口。都不是兼容性故障，但属于"下载后体验"。

## 四、代码层面的兼容性缺陷

### 4. ⚠️ **高 DPI 缩放会算错几何（P1，建议优先修）**

**现象**：在 125% / 150% 缩放（笔记本的默认设置很常见）下，拖动窗口会"跑得比鼠标快"、
贴边缩放会错位；更严重的是**窗口可能被拖到屏幕外后找不回来**（2026-09-30 那个 bug 会以
另一种形式复发）。

**根因**：挂件同时用了两套坐标，但从未换算：

- egui 的窗口矩形与 `ViewportCommand::OuterPosition/InnerSize` 用的是**逻辑点**
  （`egui-winit` 里明写 `outer_rect_px / pixels_per_point`）；
- `cursor::screen_pos()`（`GetCursorPos`）与 `screen::monitor_rect_at()`
  （`GetMonitorInfoW`）返回的是**物理像素**。

`apply_drag` 直接把物理像素的位移加到逻辑点的窗口原点上：

```rust
let d = cursor_now - session.pointer;      // 物理像素
let want = session.outer.min + d;          // 逻辑点 ← 单位混了
```

在 150% 下鼠标移动 100px，窗口会移动 100pt = 150px，越拖越偏；`clamp_origin` 又拿逻辑点
去和物理像素的显示器矩形比较，夹取失效（显示器 2560px 宽，它以为能放到 2240pt = 3360px）。
同样的问题还在：启动时的位置夹取、`remember_window_pos` 的"是否在屏内"、`auto_fit` 的
"高度不超过屏幕"三处。

本机 `pixels_per_point = 1.0`，所以开发与自测都碰不到；`cursor.rs` / `screen.rs` 的注释
也明确写着"本机 1.0，物理像素与点同值"。

**修法（建议）**：加一个统一的换算边界——
`points = physical / ctx.pixels_per_point()`；进入 Win32 侧（光标、显示器矩形）前换成物理，
发 `OuterPosition/InnerSize` 前换回逻辑点。启动时窗口还没建、拿不到 ppp，可以把"启动夹取"
推迟到第一帧（`outer_rect` 已知）再做，或按 `GetDpiForMonitor` 取。测试里用
`ctx.set_pixels_per_point(1.5)` + 假光标/假屏幕，断言"鼠标走 100px，窗口也走 100px（物理）"
以及"夹取后整窗可见"。

### 5. 中文字体是硬依赖（P2，条件触发）

字体候选依次是 `msyh.ttc`（微软雅黑）→ `Deng.ttf`（等线）→ `simhei` / `simkai` /
`simfang` / `simsun` → `segoeui.ttf`。Windows 10/11 的常规安装自带这些中文字体，
**一般没问题**；精简版镜像、Server Core、某些非中文语言包环境可能一个都没有：
程序会弹框提示，但界面上的中文（包括状态词与会话名）会显示成缺字方框，
而整个 UI 是中文的，等于不可用。

- 建议：README 写明"需要系统自带中文字体（Win10/11 默认有）"；如果要彻底消掉这个依赖，
  需要内嵌一份可再分发的中文字体（体积与授权都要评估）。

### 6. WSL / 远程机器上的会话读不到（P2）

挂件读的是 **Windows 用户目录**下的 `%USERPROFILE%\.claude\projects`。Claude Code 跑在
WSL、远程 SSH、容器里时，转录与 hook 都在另一套文件系统里，Windows 侧的挂件看不到，
hook 也不会指向这个 exe。属于"支持范围之外"，但下载者容易误解为"挂件坏了"。

### 7. 宿主进程名假定为 `claude.exe`（P3，目前成立）

`procinfo::HOST_EXE = "claude.exe"`。实测本机两种安装方式都符合：

- npm 全局安装：`%APPDATA%\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe`
- VS Code 扩展：`resources\native-binary\claude.exe`

若将来某种安装方式的宿主不叫这个名字，后果不是崩溃，而是**降级**：会话仍会显示，
但僵尸回收与"子会话不占行"的判据会失效（`claude_pid` 抓不到 → 不做存活判定）。
目前不构成问题，但值得在首次报障时先核对进程名。

### 8. 当前 Release 落后于源码（P3）

v1.0.1 发布于 2026-10-26；之后源码里已经有"窗口随会话条数自动缩放"与"未命名会话的
长标题简化"，但**没有发布新版本**。今天下载的人拿到的是旧行为。要让人下载到最新版，
需要另发 v1.0.2（对外发布需要作者拍板）。

## 五、建议的处置顺序

1. **修高 DPI 的坐标换算（P1）**——这是唯一会让"下载后正常使用"变成"窗口找不回来"的缺陷。
2. README / Release 补三段：**Windows 10/11 x64**、**SmartScreen 提示**、**context_limit 症状**。
3. 决定是否发 **v1.0.2**（把自动贴合与标题简化带给下载者）。
4. 评估代码签名（可选，成本问题）。
5. 字体与 WSL 作为"已知限制"写清楚即可。
