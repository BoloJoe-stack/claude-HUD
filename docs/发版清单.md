# 发版清单

发一次 release 的固定顺序。**顺序本身就是 2026-10-30 v1.0.2 那次留下的教训**：
当时先把 release 发了，四分钟后才提交「版本号 1.0.1 → 1.0.2」，结果 GitHub 上
`v1.0.2` tag 的源码里 `Cargo.toml` 还写着 `1.0.1` —— exe 行为不受影响（二进制不嵌版本号），
但从 tag 拉源码的人会以为拿的是上一版。

## 顺序（不许调换）

1. **先改版本号，再动其他任何东西**：`Cargo.toml` 的 `version` 与 README / Release 正文
   里出现的版本号一次改齐。`Cargo.lock` 由构建自动更新。
2. 写完本轮改动与 `docs/工作日志.md` 的对应条目。
3. `cargo test` 全绿（记下 bin / e2e 两个数，别混写「总计」）。
4. 提交并推送 `main`。**这一次提交必须包含版本号。**
5. `cargo build --release`；按 README 的 `objdump -p` 自检，导入表里不得出现
   `VCRUNTIME140.dll`（`.cargo/config.toml` 的 `+crt-static` 别丢）。
6. 打包 `claude-hud-vX.Y.Z-windows-x64.zip`（exe + README.md + LICENSE），算两个 SHA256。
7. **在版本提交上打 tag**：`git tag vX.Y.Z <版本提交>` → `git push origin vX.Y.Z`。
   打完用 `git show vX.Y.Z:Cargo.toml` 回读，确认版本号就是新版本。
8. 建 release（REST API，GitHub MCP 没有 create_release / upload_asset），上传两个 asset，
   正文写清下载物、SHA256 与压缩包内容。
9. 回读校验：`GET /releases/{id}/assets` 的 `digest` 与本地 SHA256 逐字一致；
   `/releases/latest` 指向新 tag、`draft=false`。
10. 本机换装：先停旧进程（按 PID，别用 `taskkill /IM`）→ 覆盖桌面副本 → 重启挂件 →
    截图核对。

## 版本号怎么给人看

`claude-hud.exe --version`（脚本读 stdout；没有控制台时弹对话框）。二进制没有
Windows 版本资源，右键属性里看不到版本 —— 对文件哈希只能区分是不是同一个文件，
不能代替 `--version`。
