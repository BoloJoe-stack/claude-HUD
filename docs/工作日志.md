### 交付物

```
D:\projects\claude-hud\
├─ src\            12 个模块：paths/config/model/state/hook/hooks_install/
```

**单 exe 双模式**：无参数 = 挂件；`--hook <event>` = 被 Claude Code 调用、读 stdin JSON、更新会话状态文件后立即退出（约 2ms 启动，全程静默、任何失败路径都 exit 0，绝不阻塞 Claude Code）。

**hook 已注册**到用户全局 `~/.claude/settings.json` 的 8 个事件（`SessionStart` / `UserPromptSubmit` / `Notification` / `PreCompact` / `PostCompact` / `Stop` / `StopFailure` / `SessionEnd`），全部 `async: true`、exec 形式（exe 绝对路径 + `args: ["--hook"]`，不过 shell）。

### 关键设计约束（违反其一即为缺陷）

- **零网络**：不发 HTTP、不起端口、不调 API、不写数据库。全部本地文件读写。
- **挂件绝不写状态文件**（Ruling #6）：每个状态文件只有一个写者 = hook 侧。挂件内存里的副本可能陈旧，回写会覆盖 hook 刚写下的 `state=waiting` —— **原子写只保证不读到半截文件，不保证不丢更新**。故 `transcript_offset` 与 `Delta` 只活在挂件进程内存里。
- **上下文上限手配、永不推断**：见下方「承重结论 1」。
- **会话标识只用 hook payload 的 `session_id`**；**`cwd` 只用 payload 的**（`~/.claude/projects/` 的目录名是有损编码，中文全变 `-`）。

### 承重结论 1：上下文上限必须手配（不可推断）

转录里**只记 `deepseek-flash`**，env 里配的 `[1m]` 后缀**根本不进转录**，且全文**没有任何窗口大小字段**。业界通用做法（从模型 ID 推断上限）在这里会把它判成 200K → **上下文百分比静默算错 5 倍**，且不报错、数字看起来完全合理。

→ 上限是显式配置项，默认 `1_000_000`，**不做任何自动推断**。

### 承重结论 2：Esc 打断不触发任何 hook

不处理的话，被 Esc 打断的会话会**永远卡在「工作中」**。唯一能看见它的是 transcript 里 `type=="user"` 行上的 **`interruptedMessageId`**。

**两处细节后来才被纠正，都很关键：**

1. **打断标记属于当前回合，新回合开始即失效。** 原先只置位不复位 → 任何曾经被打断过的会话**永久显示「被打断」**。而本机 139 个 transcript 里绝大多数含打断标记（某文件 1970 行里有 58 处，打断后会话还继续了 1800 多行）。**这还会让验收给出假绿** —— 「按 Esc 变被打断」那条会"通过"，因为**所有**会话都显示被打断。
2. **复位要排除打断标记行自身。** 那行也是 `type=="user"` 且不含 `tool_result`，**满足复位的判据** —— 按字面实现会在同一行上把刚置上的标志当场清掉，等于把「假绿」换成「永远不亮」。区分特征：打断行**顶层**有 `interruptedMessageId`、`content` 是块数组；真实用户发言的 `content` 是**纯字符串**。

**关于"数字用数码体、其他用微软雅黑"为什么不能靠字体栈实现：** egui 的字体栈是**按字形逐个走顺序**的，而 DSEG 自带拉丁字母 → 字母会被它抢走（用户第一版就觉得"不太好看"）。正解是**建一个只含 DSEG 的独立字体族**，只给数字段用 `FontId`；或**把 DSEG 做子集**（若做子集，注意 SIL OFL 条件 3：修改版**不得沿用保留字体名 "DSEG"**，必须改名，且修改版仍须以 OFL 分发）。

### 方法论留痕（值得沿用）

1. **15 次静态审查抵不上用户打开看一眼。** 逻辑验得再细，也不等于这东西能用 —— 验收清单必须包含"能读、能挪"这类最基本项。

### Important（已修）

**`looks_like_font` 的注释声称挡住"截断文件"，实际只看前 4 字节 magic —— 而截断恰恰保留 magic。**

后果不是理论上的：`epaint-0.36.2/src/text/fonts.rs:990` 在解析失败时是
`unwrap_or_else(|err| panic!("Error parsing .. TTF/OTF font file: {err}"))`；配上
`#![windows_subsystem = "windows"]`，进程 panic 就是**无声死亡** —— 没有窗口、没有对话框，
用户看到的是"双击了，什么都没发生"。一份被写坏成 ≤32 字节残桩的 `msyh.ttc` 仍以 `ttcf`
开头，会被放行，然后在第一帧 panic（复审实测：截到 4/12/16/32 字节都 panic，64 字节以上
才是静默退化）。

**修法**：`looks_like_font` 连**长度与表目录的自洽性**一起查（`sfnt`：`numTables > 0` 且
`len >= 12 + 16 * numTables`；`ttcf`：`numFonts > 0`、偏移表放得下、每个偏移都指向文件内
一个能放下 12 字节头的位置）。另加**全局 panic hook**（`main.rs`）把任何 panic 从"写 stderr"
改成弹框 —— 后者覆盖校验没能穷尽的所有 panic 来源。

> ⚠️ **复审给的另一条替代修法是错的，已实测推翻**："给 `set_fonts` 那一处加 `catch_unwind`"
> **拦不住**。`Context::set_fonts` 只做 `mem.new_font_definitions = Some(..)`
> （`egui-0.36.2/src/context.rs:2117`），真正的解析发生在**帧开始时**的 `Fonts::new`
> （`epaint fonts.rs:974`）。要 catch 得包整个帧循环，那会把 egui 留在半初始化状态。
>
> ⚠️ **panic hook 必须跳过 `--hook` 模式**：那条路径被 Claude Code 调用，硬性要求静默、快速
> 退出、失败也 exit 0。一个模态框会挂在 Claude Code 的调用链路上等用户点"确定"。

## 2026-09-15 · 9b 僵尸会话：取证 → 裁定 → 实现

> 本节把上一节"仍未做 / 开口"里的最后一条结清（`%TEMP%` 根因与"中文字体缺失无提示"已在上一轮的修复提交 `72d0b7a` 里做完）。

### 一句话

9b（spec §7 坑 2，僵尸会话）悬了很久，**直接原因**是原方案的硬伤：hook 进程的环境变量
**无法由外部注入，必须在 Claude Code 启动时就带上** —— "测一次"的代价是重启整个
Claude Code。这一轮先给探针加了一条**运行时启用**的路把测量做掉，再按结论实现。

### 一、先把"测不了"变成"可测"（`72d0b7a`）

加哨兵文件 `%APPDATA%\claude-hud\ppid-probe.enable`：**运行时**读，创建即生效，不用重启。
它**只写文件、不弹框**（安静模式下每个事件都会跑探针，模态框会糊满屏幕、还会挂在
Claude Code 的调用路径上）；环境变量那条保持"响亮"（写文件 + 弹框）。

探针改成**追加写**并记 `session_id` 与事件名 —— 这一步是必需的，见下面的误判。

### 二、取证：5 份样本，结论确定

| session_id | 样本 | `nearest_claude_pid` |
|---|---|---|
| `8b4d0f26…` | 3（`Stop` / `Notification` / `UserPromptSubmit`） | **恒为 20232** |
| `2c9e5a47…` | 2（两次 `UserPromptSubmit`） | **恒为 3528** |

- hook 的 **hop 1 就是 `claude.exe`**，**没有中间 shell**（注册是 exec 形式、不过 shell）。
- **宿主 pid 对同一个 `session_id` 恒定**。

⇒ **裁定：保留 `claude_pid`，走真实存活检测**，不引入超时回收旋钮。

> ⚠️ **取证中途我误判过一次，值得记下来。** 头两份样本（当时还是覆盖写、不带 `session_id`）
> 的宿主 pid 不同，一度像是"宿主会变、`claude_pid` 不可靠"。补上 `session_id` 才看出那两份
> **本来就来自不同会话** —— 本机同时开着 **3 个** `claude.exe`。查进程表确认后，疑问当场消失。
>
> **教训与 09-14 那次同源：手边一次观测不能当结论。**（那次是拿 bash 手调的拓扑当结论。）

### 三、实现

| 位置 | 做什么 |
|---|---|
| `src/procinfo.rs`（新） | 进程表查询从 `probe.rs` 搬出来独立成模块 —— 9b 给了它真实消费者，它不再是"调试专用"。父进程链、`nearest_named`、`alive` 都在这里。 |
| `hook.rs` | `SessionStart` 时抓一次 `claude_pid`（`capture_claude_pid`）。 |
| `ui.rs` | 每轮判存活；`dead_streak` 跨轮持有（与 `offsets` 同理）；标 `host_gone`、连续两轮后移除。 |
| `view.rs` | `Row.host_gone` + `mark_host_gone`（标位并把僵尸行**稳定地**沉到最后）。 |
| `ui.rs` 渲染 | 僵尸行显示灰色「已退出」，**取代**状态词。 |

**三处选择各有理由：**

1. **`claude_pid` 只在 `SessionStart` 抓。** `snapshot()` 枚举整个进程表实测 **7.5 ms**
   （release 与 debug 几乎一样 ⇒ 是内核枚举的代价、不是 CPU）；hook 本来约 2 ms，放进
   每个事件会让它慢 4~5 倍。宿主 pid 既然恒定，抓一次就够。
2. **判存活用 `OpenProcess` + `QueryFullProcessImageNameW`，不枚举全表**：微秒级。
3. **判不准时一律判"还活着"。** 误判成"已退出"的后果是把这个会话从界面上抹掉；而这是个
   帮人看"谁还在跑"的工具，**最糟的错法就是让活着的会话消失**。`claude_pid` 为 `null` 时
   **完全不判定**。**宁可漏报僵尸，不可误杀活人。**

**"已退出"不是 hook 产生的状态**，而是挂件推导的**显示覆盖**：宿主都死了，不会再有 hook 事件，
"最后一个事件报的状态"会永远停在那里 —— 所以由挂件在渲染时取代它。表现按用户裁定：
**先标灰「已退出」，连续两轮确认后再移除那一行**。

### 四、反向对照抓到一条会线上发病的 bug

按上一轮的教训，给 `alive` 的正向路径加了**反向对照**：
`alive_recognizes_a_real_running_host_if_one_is_present` —— 拿**真在跑的** `claude.exe` 验它

```
C:\Users\…\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe.old.1789424350591
```

而 Toolhelp 的 `szExeFile` 报的仍是**原名** `claude.exe` —— 同一个进程，两条路子给的答案不同。
我按"取 basename 再判相等"实现，于是**本机 3 个真在跑的 `claude.exe` 全被判成"已退出"**。
线上症状会是**挂件里的会话一个个莫名消失，且不报错**。

改成"相等，**或以 `claude.exe.` 开头**"（`claude.exefoo` / `notclaude.exe` 仍不算，保住
pid 复用的防护价值）。修完反向对照转绿：**已核验 3 个真在跑的 claude.exe 全部判为存活**。

> **这是本项目第二次由"反向对照"直接拦下线上事故**（第一次是字体校验过严会让中文整屏方框）。
> 共同点：**正向路径不报错、只是安静地做错**，静态审查和普通单测都看不见。

### 二、bug 1：标题每隔几秒闪一下

**现象**（用户）："现在的标题过一会会弹出其他东西来，我希望标题固定不动。"

**根因是双重的，两层都在我们这边：**

1. **空闲轮会掉回目录名。** 状态文件**每轮都从磁盘重读**，而盘上的 `display_name`
   **恒为 `None`**（挂件不写回 —— Ruling #6；hook 也读不到 transcript）。而标题原来只在
   **"本轮读到了新字节"**那条路上赋值 —— 于是空闲轮 `read_new` 返回 `None`、`refresh`
   在读之前就 return，**标题掉回 cwd 末段**。表现就是标题在"真标题"和 `claude` 之间闪。
   → 改成**从内存里跨轮保留的 delta 定标题**，并且放在 `refresh` 的**最开头**（任何 `return`
   之前）。
2. **兜底档会随对话一直变。** 我们照 VS Code 抄了 `lastPrompt`（最后一条 prompt）当第三档
   —— 它每次发言都变。→ **跳过它**，改用 `firstPrompt`（first-wins，天然稳定）。
   **这是与 VS Code 的一处有意偏离**，理由是挂件常驻桌面、而 VS Code 的会话列表只是一次快照。

### 三、bug 2：后台子代理被当成已经跑完

**现象**（用户）："主 agent 停止工作了，但是子代理还在工作，HUD 里应该显示工作中才对。"

**根因**：后台子代理的 `tool_result` 是**启动回执**，不是完成 —— 内容是
`Async agent launched successfully… The agent is working in the background`。
而我们的判据是"收到 `tool_result` 就算这个代理结束了"，**于是它一启动就被移出"在跑"集合**。
主代理的 `Stop` 已经把状态推到"完成"，两者叠加 → 显示"完成/待命"，**与事实相反**。

**改法**：把"在飞"拆成两个集合 —— 前台（收到 `tool_result` 即完成）与**后台**
（等到 `<task-notification>` 才算完）。`subagent_count` 取两者之和；打断时**只清前台**。

**取证（真机转录，逐行解析）**：

- `<task-notification>` 的 `<status>` **只有** `completed`(144) / `failed`(3) / `killed`(3)，
  **没有 `running`**，且**全部带 `<tool-use-id>`** ⇒ 见到匹配 id 即可移除。
- **前台代理不发通知**（多数会话"启动回执 = 0"），它们的完成信号就是自己的 `tool_result`。

> ⚠️ **已知脆弱点**：启动回执**没有结构性标志**（块的字段与普通工具结果完全一样），判据只能
> 是**文本匹配**。Claude Code 一改措辞就会**静默失效**、本 bug 复发。故同时认两句措辞以降
> 单点失效概率，并配了**双向**变异测试（判据恒 `false` 与恒 `true` 各红一次）。

### 四、⭐ 一个"测量污染自己"的坑

数 `<task-notification>` 的状态分布时，我先用 grep，得到 **`running` 出现 20 次** ——
**而那 20 次正是我自己上一条命令的输出被记进了转录**。**我的测量污染了自己的输入。**

改用 python 只解析真正的 `<task-notification>` 块之后，才得到正确的分布（只有三种状态、没有
`running`）。**如果照第一版的数去实现"只认终止态、跳过 running"，代码里会留下一条永远走不到
的分支，而我会以为它防住了什么。**

> **规矩：凡是"grep 一个语料，而自己刚往同一个语料里写过东西"的场合，都会踩这一脚。**
> 这类语料包括：转录（我们自己的工具输出会被记进去）、`%TEMP%`、测试目录、日志。

### 五、另外两次"测试写错了，不是代码错了"

## 2026-09-15 晚 · 第三轮外观：右缘基准 + 四段纵向间距

### 一句话

用户一句"**状态词+计时右对齐到右缘**"，做下去发现**纵向间距必须一起重定** —— 两件事同一个根因：
间距一直是**隐式份量叠出来的**。本轮把三处隐式份量全部消掉、立了两条右缘基准、把四段间距
重新裁定并**逐段钉进测试**。

### 一、根因：间距从来不是常量，是"常量 + 三处看不见的东西"

三处隐式份量（**都是查 egui 0.36.2 源码 + 真帧实测核过的**）：

| 隐式份量 | 来源 | 对策 |
|---|---|---|
| `item_spacing.y` = **3**（不是 8！） | egui 每次 `add` 后自动追加。`Spacing::default()` 是 `vec2(8.0, **3.0**)` —— `.x` 才是 8 | 面板级 `spacing_mut().item_spacing.y = 0.0`（**只清 `.y`**：横向的 `item_spacing.x` 还要给 `name_budget` 用） |
| `ui.horizontal` 的块高 **+5** | 由内容推出，且**随混排字号变**（第二行比它最高的 galley 还多 5pt，**第一行恰好不多**） | `row_line()`：`allocate_ui_with_layout` 显式钉死行高 |
| `separator()` 的占位带 = 6pt | 线画在 6pt 带的正中间（`SeparatorStyle::spacing = 6.0`） | `rule()`：`spacing(0.0)`，线落在游标当前 y 上 |

> ⚠️ **"写 33 得到 29、写 11 得到 19"这两句已作废**（2026-09-16 复审抓出，我用探针在两版上复量确认）：
> - `29`/`52` 是**每会话三行**那个版本（`881e951`）量的，而三行布局第二天就被用户否掉了。
>   本轮基准版（`a407ba7`）的同一对量是 **58 / 88**——所以"改前 add_space(33) 得到 29"**在本轮基准版上不成立**。
> - `19` 也不是"隐式间距"：它是 `11 + 第二行自己的 ink 高(8)`，那 8 是**字高**不是间距，而且它挂在
>   "第二行 → 分隔线"上、却被写进了"第一行 → 第二行"那段。**照它推会得出"add_space 会额外多给"，
>   那是错的**（`add_space` 是 1:1 的，多出来的是行高与 `item_spacing`）。
>
> **能复现的版本**（我自己跑出来的）：基准版 `EXTRA_ROW_GAP = 33` → 量到 **58**；本轮把行高与三处隐式量
> 清掉之后，**同一个 33 只量到 49**（`cargo test rows_are_spaced` 的失败信息里就打着这个数），补到 42 才回到 58。

> **规矩：凡是"间距"就不允许有隐式份量。** 否则"改 14"和"界面变成 14"是两件事，
> 而测试若断言常量，它会跟着一起动 —— **变异照样绿**。

### 二、右缘基准：不能用 `with_layout(right_to_left)`

egui 没有"第二组靠右"的原语，惯用法是 `with_layout(Layout::right_to_left(..))`。**实测在
本文件这种"上一段是截断过的会名"的场合它是坏的**：**分配**对（`min_rect` 正好到内容右界）、
**绘制**却从 `max_rect.right()` **往右**画 —— 220pt 窗宽下 `00:41` 被画成 `00:4` + 半个 `1`
（最后一个字形被面板裁掉半截）。

→ 改成 `paint_right()`：**自己算落点、直接 `painter.galley`**（右缘 = `max_rect.right()`，
每段再向左让出自己的宽度；垂直按行高居中）。**顺带的收益**：落点由我们决定，于是
"右缘贴齐"**可以被单测断言** —— 走 `with_layout` 时 `Shape::Text.pos` 报的坐标是错的，测不了
（这是**"测不了 ⇒ 只好换个实现"**：可测性反过来选了实现）。

### 三、四段纵向间距（改前 → 裁定）

| 空隙 | 改前 | 裁定 | 为什么 |
|---|---|---|---|
| 顶栏 → 第一条会话 | 6pt | **16** | 6pt **比会话内部两行之间的 8pt 还紧** —— 次要信息与正文之间的空白比正文内部还小，层级是倒的 |
| 第一行 → 第二行 | 8pt | **14** | 改前第二行离**下面的线**（11）比离**它注释的那一行**（8）还远，读起来是不属于任何一边的掉队注脚 |
| 第二行 → 分隔线 | 11pt | **8** | 与上一条配对成"上大下小"，第二行才明确属于上面那一行 |
| 第二行 → 下一会话会名 | 58pt | **58pt 不变** | 旧裁定**不许被这一轮悄悄推翻**，故按实测净减补了 `EXTRA_ROW_GAP` |

> ⚠️ **上表口径**：前三行量的是**视觉空隙**（前一段 ink 下缘 → 后一段 ink 上缘）；
> 第四行的 58 是**galley 原点差**（同一处的视觉空隙是 **50**，差的那 8 是第二行自己的字高）。
> 两种量**别混着比** —— 照上表口径去验收的人，量第四行会得到 50 而不是 58。

**一条关于"怎么测分区感"的坑**：第二行的 **origin 间距改前是 30pt（改后 36）、看着很健康**，但它在屏幕上
离下面的线仍然更近 —— **因为它只有 8pt 高**。判断分组感要量**视觉空隙**（前一段的 ink 下缘 →
后一段的 ink 上缘），**不是 galley 原点的差**。
（`27/33` 那两个数作废：2026-09-16 我用探针在两版上复量，真值是 **30 / 36** —— 差 3 恰好是当时还没清掉的
`item_spacing.y`，也就是说那两个数是在**中间态**量的、不描述任何一个被提交的版本。）

## 2026-09-16 · 第三轮的 scoped 复审（三席）+ 修复轮

### 一句话

### 一、Critical：会名真的会压在「已退出」上（`host_gone` 分叉）

**现象**：宿主进程已退出的会话，会名会**叠在**状态词上。

**根因是教科书式的"两处各算一遍"**：`name_budget` 按 `state_label(row.state)` 扣额度（「完成」= 30pt），
而 `draw_row` 在 `host_gone` 时画的是 `EXITED_LABEL`「已退出」（= 45pt）。改前状态词是顺序左排的，
最坏结果是被挤出去；**本轮右组改成"画在固定位置、不参与布局"，同一个错算就变成叠字** ——
从"右缘被裁"（一眼能看出是 bug）变成"会名尾巴压在「已」上"（更难发现）。

**我自己的探针实测**（220pt / 默认 320pt）：

| 窗宽 | 会名 | 会名右缘 | 「已退出」左缘 | 结果 |
|---|---|---|---|---|
| 220 | `abcdefghijklmnopqrstuvwxyz` → `abcdefg…` | **109.09** | **104.03** | **压 5.06pt** |
| 320 | `claude-hud 右缘基准那轮` | **208.66** | **204.03** | **压 4.63pt** |
| 320 | 同上拉丁长名 | 206.31 | 204.03 | 压 2.28pt |

**修法**：把"这一行到底画哪个标签"收成**一个函数** `state_text(row)`，`name_budget` 与 `draw_row`
都调它 —— 消掉"只有一处改"的结构性隐患。修完最坏情况余 **9pt**（= `item_spacing.x` + `WIDTH_RESERVE`）。

**测试也一起补**：那条自称"最坏情况"的守卫用例原先只测 `State::Working` + 非 gone 的行
—— **唯一会分叉的格子恰好就在它旁边**。现在四档 × 两个宽度都测。变异验证：把额度改回
`state_label` → 红，失败信息打出的正是 "109.09375 撞上了 '已退出' 左缘 104.03125（压 5.0625pt）"。

> ⭐ **本席位的教训**：**"某条不变量有测试守着"这句话，必须连"守的是哪几格"一起说。**
> 一个只覆盖了"不变量恰好成立的那一格"的测试，比没有测试更危险 —— 它会让下一个人不去看。

## 2026-09-16 · 用户实机报的 bug："任务已经结束了还显示工作中"

### 一句话

### 一、现象与定位

用户实机看到：**某个会话里任务早就结束了，挂件仍显示"工作中"**。

我先按 `state = Working if subagent_count > 0 && state ∈ {Done, Idle}`（第三轮加的那条
"后台子代理在跑时显示工作中"）去查，发现**后台代理集合只增不减**。用项目自己的
`parse_delta` 跑本会话真转录：`bg_agents` 里躺着 **6 个**早已结束的代理 —— 于是主代理
`Stop` 之后状态被这条规则一直顶成"工作中"。

### 二、根因 1：**完成通知从来就没被读到过**

后台代理的完成信号是 `<task-notification>`。上一轮我取证时是**grep 原文**找到它的
（366 条），**但从没核过它长在哪一行上**。真身是：

```json
{"type":"queue-operation","operation":"enqueue","content":"<task-notification>…"}
```

—— 通知在**顶层** `content`、而且是**字符串**。而解析器只在 `type == "user"` 的分支里找它。

**全机取证**（36 份转录）：带 `<task-notification>` 且 `content` 是顶层字符串的行 **366 条，
全部是 `queue-operation`**；挂在 `user` 行上的 **0 条**。也就是说那条判据**在真实数据上
一次都没命中过** —— `bg_agents` 只进不出，第三轮那个功能从上线起就是坏的。

> ⭐ **那条测试为什么给假绿**：它的 fixture 写的是 `{"type":"user","message":{"content":"<task-notification>…"}}`
> —— 一个**在真实语料里根本不存在**的形态。测试于是测的是一个不存在的世界。
> **夹具必须逐字取自真机，且"这条 fixture 的形态在真数据里存在吗"要单独确认一次。**

**修法**：按**结构**认通知行（`is_notification_carrier` = 顶层 `content` 是字符串且含
`<task-notification>`），并**移到 `match` 之外**——否则再"结构正确"也还是只在 `user` 分支里跑。

### 三、根因 2：**"幽灵代理"**（同一个 bug 的另一半）

修完上面那条，真转录里还剩 **4 个**清不掉的代理。它们的 `tool_use_id` **不对应任何
`Agent` 调用** —— 是**我自己**在调查这个 bug 时，用 `Bash` 探针把转录片段打印出来，
那段文字里恰好含着启动回执的措辞（`Async agent launched successfully`）。

而 `bg_agents.insert()` 是**无条件**的：只要哪个 `tool_result` 里出现那句措辞，就插进去。
于是**任何**一次 grep 源码、读 `transcript.rs`、打印转录，都会凭空造出**永远收不到终止
通知的**幽灵代理 —— "子代理 N"与"工作中"从此永久挂着。

**修法**：插入前先 `d.pending_agents.remove(id)` 成功（= 真解析到过对应的 `Agent` `tool_use`）。
文本匹配只作为**二次确认**，不再当**唯一判据**。

> 这正是本仓记过的"**测量会污染自己的输入**" —— 只不过前几次污染的是**我的分析结论**，
> 这次污染的是**产品状态**。规矩升级：**凡"从语料里 grep 出一句话来当下判据"的场合，

## 2026-09-16 · 用户报的第二个 bug："在工作却显示等待确认/完成"

### 一句话

**不是延迟**（用户猜的是延迟）—— 是状态机**缺两条出路**：有两段真实的工作期，
**一个 hook 事件都不会发**。修复靠"转录动过没有"这个唯一能看见"此刻真的在动"的信号。

### 一、根因（从 `model::transition` 的表里直接读出来的，不需要碰运气）

已注册的 8 个事件里，**"等待确认"的出路**只有：下一次 `UserPromptSubmit`、`Stop`、
`StopFailure`、`PreCompact/PostCompact`、`SessionEnd` —— **全在回合边界上**。于是：

| 场景 | 发生了什么 | 界面 |
|---|---|---|
| **权限批了之后** | `Notification(permission_prompt)` → 等待确认；用户点"允许"**不触发任何已注册事件** | 从批准到回合结束，一直显示"等待确认"——**人却在看它疯狂干活** |
| **后台子代理干完、主代理被自动唤醒** | 这种回合由 `<task-notification>` 驱动，**没有 `UserPromptSubmit`** | 上一个 `Stop` 留下的"完成"一直挂到回合结束 |

**两段症状一样**，用户看到的就是这两段。

### 二、修法：**活动胜过终态**

转录是**流**，状态文件只在事件边界更新 —— 所以"转录在本状态定下来之后又动过"就是
"它其实在干活"的证据。`Delta` 新增 `last_line_at`（跨轮保留、取 max），
覆盖规则：`last_line_at > state_since + 2s` 且状态是 `Waiting`/`Done` ⇒ 显示工作中。

**三处小心（都写进注释了）**：
1. **只覆盖 `Waiting` 与 `Done`** —— `Error`（API 挂了）是"要你动手"的档，被顶掉就把该看的提示藏了。
2. **留 2 秒余量** —— `Stop` 是读完转录才发的（payload 里带 `last_assistant_message`），
   正常情况下最后一行早于 `state_since`；但毫秒级抖动会让每个回合末闪一下"工作中"。
3. **真在等授权时不会误判** —— 那时主代理**阻塞**，转录不写新行，`last_line_at` 停在发起工具调用那一刻。

> ⭐ **通用教训**：**"事件驱动的状态"必须有一个"证据驱动的兜底"。**
> 状态机只认识事件边界，而"人是不是在干活"这件事**没有事件**。
> 本项目之前那条 `Interrupted`（Esc 不触发 hook）是同一个形状 —— 这次的转录活动信号
> 其实可以顺手把那一类也兜住。

3e7a1c85 晚 569s）⇒ 覆盖生效。

## 2026-09-16 · 新计划开工：token 视图（T1–T4）+ 一条"数会虚高 2.29 倍"的发现

### 一句话

新计划的前四个任务落地：**今日 token 账本 + 扫描器 + 顶栏/行尾渲染 + 子代理 ∟ 折线**。
其中 T1 被一条实测推翻过一次 —— **按行累加 token 会虚高 2.29 倍**，而这条是我派去采夹具的
子代理挖出来的（它不在任务清单里）。

### 一、⭐ 承重发现：一次 API 响应会写成多行

**一次响应在转录里写成多行**（`thinking` / `text` / `tool_use` 各一行），
**每行 `uuid` 都不同**、`message.id` 相同、`usage` 基本相同。我自己复核过（同一文件连续三行，
`message.id` 全是 `a928250d…`，usage 全是 563762/4755/4096/0）。

于是**按行累加 = 把同一次调用算好几遍**：

| 口径 | 今天 |
|---|---|
| 按行累加 | **403.2M**（虚高 2.29 倍） |
| 按 `message.id` 归组、组内取时间戳最大的一行 | **175.8M** ✅ |

全机：今天 **2245 行只对应 965 个 `message.id`**；`uuid` 去重**救不了**这个（那几行 uuid 本来就不同）。

组内为什么取"时间戳最大"：实测 19,799 组里，最后一行的 `output_tokens` **100% 是组内最大值**
（零反例）—— 中途的行写着 `output_tokens: 0`（那一刻还没生成完）。另有 **394 组文件顺序与
时间戳顺序不一致**，所以判据不能是"最后读到的那行"。

### 二、修法与验证

`Ledger` 从"uuid 去重集合"改成"**记下每组采信的那一行**"，新行更晚时**先把旧贡献减掉**再记新的
（只加不减就是虚高那版）。没有 `message.id` 的行退回用 `uuid` 当键。

| 变异 | 结果 |
|---|---|
| 退回按 uuid 去重 | **RED**（"只该算一次…按行累加会是 156534"） |
| 替换时忘了减旧值 | **RED**（"替换而不是叠加（叠加会是 2500）"） |

**修复前后真机对数**：395.7M → **182.9M**，与独立 Python 脚本的 175.8M 吻合（差的是测量间隔里
我自己的会话还在长）。

## 2026-09-16 · 行首色条改成"每会话一个颜色"

## 2026-09-16 · 色块：改成"红黄蓝绿"、画成矩形、保证可见会话不撞色

用户看过上一版（`session_id` 哈希 → 8 色淡雅色板）之后："**不明显，就用红黄蓝绿**、**色块稍微大一点**"。

### 一、色板 → 红金蓝绿

- **"黄"只能是深金 `#a16207`（4.92:1）**：亮黄在白底的对比度只有 **1.1:1**，怎么调都过不了 AA。
  这是色相里最接近"黄"又满足对比度的那个，**不是审美选择**。
- 色板 6 色：红 `#b31f1f` / 金 `#a16207` / 蓝 `#1565c0` / 绿 `#0f6b2e` / 紫 / 石板蓝（后两支给第 5、6 条）。
- ⚠️ **这四支与状态色重合**（红=出错、金=等待确认、蓝=完成、绿=工作中）。这是"明显优先"的代价：
  **色块只表示身份，状态由状态词的颜色与文字表示**。已写进 spec，免得下次有人把两者混起来。

### 二、`▍` 字形 → 矩形

原来那根条是**字体里的半块字符**（U+258D）。放大它有两个掣肘：字号一大，行高
（= 该行最高字块的 max）跟着涨 ⇒ **四段纵向间距全要重标**；而且它**依赖中文字体提供这个字形**。

改成 `painter.rect_filled`（8 × 20pt、圆角 1pt）：尺寸由常量决定，与字体、行高都解耦。
顺带把"字体覆盖"测试里那条 `▍` 去掉了 —— **字体不再需要这个字形**。

### 三、颜色分配：三条性质，第二条是重写的

第一版是**逐行贪心**（"自己的哈希色被占了就取第一个空的"）。写测试时发现它**与行序有关**：
换个顺序，先来的那条会把色占掉，整片颜色都变。而用户要的是"记住红块那条是调研"。

改成**与顺序无关**：先按 `(哈希色下标, session_id)` 排序再分配，最后按原顺序放回。于是：

1. 同时可见的会话**互不同色**（≤6 条）；
2. **与在列表里的位置无关**（排序键里没有行号）；
3. 会话集合不变时**颜色不变**。

三条各有一个断言，另配变异验证（同色化 / 贪心版各红一次）。

## 2026-09-17 · 修"不能调整大小"（最外一圈是死区）+ 最小尺寸有依据了 + 不画半条会话

### 一、⭐ 根因：最外一圈是死区（**我先量、后动手**）

缩放判定与"按下"的接收区域都挂在**面板内容区**（`ui.max_rect()`）上，而内容区比窗口小 8pt：

| 距窗口边缘 | 按下会发生什么（旧代码） |
|---|---|
| **0 ~ 8pt** | **什么都不发生** —— `ui.interact` 的矩形不含它，连拖动都收不到 |
| 8 ~ 14pt | 才算"边缘 → 缩放"（内容区外扩 `RESIZE_BORDER` 6pt 的结果） |
| 更内侧 | 拖动 ✓ |

**而人抓边框，手就是往最边上放的** —— 黑边一去掉（视觉上的边 = 窗口边）更会如此。
于是"最边上按下去毫无反应"，看起来就是不能缩放。

**修法**：`window_rect()` = 内容区外扩一个内边距 ⇒ 整块窗口都可交互；抓取带 6 → **8pt**。

### 二、既有的那条端到端用例为什么没抓到

`handle_window_drag(ui)`**、**没有经过 `CentralPanel` 的内边距** —— 在它那个夹具里
"内容区 == 窗口"，**压根不存在那一圈死区**。

> ⭐ **夹具与真实调用链不一致，测的就是另一个世界。** 这与本仓另外两条同源：

## 2026-09-17 · 缩放改成"自己做"（`BeginResize` 在无边框窗口上不生效）+ 光标

以及含它们的角）才发作；拖右缘、下缘时原点不动，那条回路压根不成立。

### 二、怎么定位的（先证伪了三个假设）

自动模拟接管鼠标（脚本见 `临时文件\hud-drag-sim\drag_sim.py`），配合两个**临时的 env 开关探针**
（查完已删）。中途推翻的假设，都留痕：

| 假设 | 结果 |
|---|---|
| 呼吸动画的重绘把 CPU 烧干 | ❌ 带呼吸跑满 90 秒，内存**平在 355.5MB**、CPU ~7% |
| 呼吸动画每帧换颜色 ⇒ egui 布局缓存泄漏 | ❌ 同上，内存一动不动 |
| 拖动期间"每帧发窗口移动命令"频率被动画放大 | ❌ 把动画帧停掉（`req=1000`）**照样卡** |

**决定性证据**（几何探针，按住左缘不动 6 秒）：

```
拖前       5942×380
1s        6088×380
3s        6260×380
6s        6582×380        ← 还在涨
最终      -4020,523  6582×380   ← 原点跑到屏幕外
```

同时 `d` 每帧固定 +8pt，而**指针全程没动** —— 这就是正反馈的形状。

### 三、根因

缩放是"每帧自己算"：`d = (窗口原点 + 指针的窗口内坐标) − 按下时的位置`。

这两个数**时刻不同** —— 原点是 egui **现在**报的，指针是它**上一帧**收到的。
窗口一移动，指针的"窗口内坐标"就跟着变，于是**窗口自己的位移被再算一遍成"鼠标移动了"**：

```text
估出来的光标屏幕坐标 = 原点(现在) + 指针窗口内坐标(旧) = 真实光标 − 窗口位移
```

每帧多推一点 → 窗口越滚越远、越撑越大 → 渲染越来越慢 → 最后死掉。
**用户报的"拖动很慢，然后进程终止"就是这个链条。**

探针还实测到一件反直觉的事：拖动期间 egui 手里那份指针窗口内坐标会**僵在旧值**
（`ptr` 全程 = 1 而窗口在跑）。所以"换个原点去加"这条路走不通 —— **只能换数据源**。

### 四、改法

- 新增 **`src/cursor.rs`**：Win32 `GetCursorPos` 直接要光标的**屏幕坐标**，与窗口在哪毫无关系
  ⇒ 回路不存在。（不引新依赖，与 `procinfo` / `dialog` 同一套 `#[link]` 写法。）
- 光标来源以 `&dyn Fn() -> Option<Vec2>` **注入**：生产传 `cursor::screen_pos`，测试传夹具 ——
  真实的 `GetCursorPos` 在无头环境里不可控，而本次的关键恰恰是"光标不动时几何不许变"。
- 拿不到光标时**这一帧什么都不做**：少发一帧命令无害，拿错数会把窗口推着跑。

守它的那条测试 `resizing_from_the_left_edge_converges_while_the_cursor_stands_still`
**夹具照实模拟了两件事**：① 窗口系统真的按命令移动窗口（`viewport().outer_rect` 每帧在变）；

## 2026-09-18 · 子会话不再占行（"我明明是四个却显示六个"）+ 缺 pid 的会话会被补抓

用户报："显示的会话名字和实际不一致 …… 我明明是四个却显示六个，一致倒是一致的。"
**名字是全对的**，错的是**条数**：4 个是他自己开的，另外 2 行是**他某个会话里跑出来的
`claude -p` 子进程**。

### 一、取证（真机，不是读代码想出来的）

同时开着的 6 行里，两条 `estimate.rs 成本…` 的进程链是（`Win32_Process` 逐跳抄下）：

```text
claude.exe(32072 / 30828)          ← 被当成"会话"各占一行的那两个
 ← python.exe ← py.exe ← bash.exe ×3
   ← claude.exe(29072)             ← 用户自己的「RS MCP token消耗实验」会话
```

命令行是 `claude.exe -p --output-format json --strict-mcp-config …`。**子进程自己也是一个会话**、
也写状态文件，挂件就照单全收。用户开 4 个 → 界面 6 行。

顺带挖出**第二个缺陷**：`样例系统` 那行的 `claude_pid` 是 `null`（`SessionStart` 时没抓到），
而挂件对 `null` **不做存活判定**（9b 的安全阀）⇒ 它退出后会**永久留在列表里**，永不回收。

### 二、改法

| # | 改哪 | 怎么改 |
|---|---|---|
| 1 | `procinfo::host_and_parent`（新） | 同一张快照回答两问：宿主是谁、**宿主之上还有没有第二个 `claude.exe`**。判据只用父链**形状**，不解析 `-p` 之类旗标（旗标随版本变，链的形状是 `CreateProcess` 的必然后果） |
| 2 | `state::SessionState.nested`（新，三态 `Option<bool>`） | hook 在 `SessionStart` 写下这个事实；`true`=子会话、`false`=查过了不是、`null`=**改造前的老文件**（挂件按"用户自己开的"处理） |
| 3 | `ui::poll_once` | `states.retain(\|s\| s.nested != Some(true))` —— **只藏 `Some(true)`**，放在解析 transcript 之前（子会话的转录不必解析） |
| 4 | `hook::should_capture`（新） | 补抓：`SessionStart` 必抓；**其余事件只在还没 pid 时**抓。抓到一次就停 ⇒ 不是热路径开销（hook 全是 `async: true`） |

**口径是用户拍的**（两问两答）：子会话**完全不显示**（不占行、不标注）；第二个缺陷**一起修**。
零额外 syscall：宿主 pid 本来就要在 `SessionStart` 枚举一次进程表（7.5 ms），第二问用的是同一张快照。

### 三、验证

| 项 | 结果 |
|---|---|
| 测试 | 基线 **235 + 2 = 237** → **241 + 2 = 243**（+6）；警告仍 **5 条**（不加 `#[allow]`，顺手删掉被取代的 `capture_claude_pid`） |

### 四、三笔要如实记的账

1. **第一条变异选错了杠杆**：我对 `nested` 删 `#[serde(default)]`，测试**照样绿** —— 因为 serde 对
   `Option<T>` 本来就容忍缺字段，那个属性在它身上是**冗余**的。换成"把缺字段的默认值给成
   `Some(false)`"才红。**结论写进 `state.rs` 的注释了：老文件读得出 `None` 靠的是 `Option` 本身，
   不是那行属性**；那行属性留着只为与邻居字段一致。
2. **判据是尽力而为**：`ancestors()` 撞到**已退出的中间进程**就断链（Windows 只给 ppid）。
   实测：我自己从 Bash 工具里用 `( … & )` 起的 `claude -p`，那个子 shell 立刻退出 ⇒ 链断 ⇒

   —— 与"浏览器要 explorer.exe 打开"同一个道理。

### 三、修：`decay` 与"转录活动覆盖"走的是两个时钟

**症状**（用户 09-16 报过的那句，上一轮只治好了一半）：后台子代理跑**超过 5 分钟**后，主代理被
`<task-notification>` 唤醒开新回合（这类回合**一个已注册事件都不发**）—— 界面上一个正在烧 token
的会话写着「待命」、计时还在走，还被排进"完成/待命"组放到列表**前面**。

**机制**：`model::decay` 在 `idle_after_sec`（默认 300s）后把 `Done` **降级成 `Idle`**，
而活动覆盖判的是**降级之后**的 `state`，只认 `Waiting | Done` ⇒ 降级后签不上名。
旁边的子代理覆盖是 `Done | Idle` —— 两处不一致，是漏了一档。

**根因之二（测试侧）**：那五个夹具全是 `state_since=100 / now=300`（相隔 200s < 阈值 300s），
**一次都没跨过 `decay`** —— 又是"夹具与真实对象不一致，测的是另一个世界"。

**改法**：`Idle` 加进覆盖。**副作用先验过**（放进去等于把这条规则从"5 分钟内"放宽到"永远"，
得确认不会把老会话永远显示成工作中）：真机上**所有真正空闲的会话，"最后一行"都比 `state_since`
晚 0 秒**（覆盖打不上），翻成"工作中"的都是真在跑的。新加的反向对照 ⑦' 守着这一条。

### 四、修：色块会自己换色

**症状**：颜色原先按"当前**可见**的那几条"分配（`assign_colors(&rows[..fit])`），而 `fit` 随
**窗口高度**变、成员又随**排序**变 ⇒ 用户什么都没做，已上屏的会话就换了色（实测：
4 条在屏 `[蓝,绿,红,金]`，第 5 条一进来 `5a0c7e13` 红→金、`9d2f6b04` 金→绿）。

**难点**：不能简单改回"对着整份列表分配"—— 那条路**当年试过并被否掉**，注释里留着现场：
"列表里可能超过色板长度，一超就从头上重复，于是看得见的那几条里就会出现两个同色
（实测截图：第 1 条与第 3 条都是蓝的）"。那条测试的 `session_id` 还是**特意挑过**的
（`t0-0 … t0-7`），专为挡住整表分配。

**改法（两步）**：

1. `assign_colors` 对**整份列表**全局定色 —— 输入只随"有哪些会话"变，窗高/排序都不再影响它；
2. `colors_for_display` **只在可见集合真的撞色**时才局部重排，且期望色取**全局色**（不是哈希色）
   ⇒ 没撞的那几条稳稳留在原地。

于是：**≤4 个会话（色板长度，也是用户声明的上限）时永不动色**，而"可见的两两不同色"一条不丢；
残留只落在"会话数 >4 且可见处撞色"这一档 —— 那一档要钉死只能让可见的两条同色，正是用户
09-16 否掉的做法，所以选了"撞色才动"（注释里写明）。

### 五、顺手：每帧白烧 172 µs

`App::ui` 每帧克隆整本 token 账本，其中 99% 花在 UI **一个字都不读**的 `msgs` 上（UI 只读
`total` / `day()` / `session_tokens()` 三样）。改成 `usage::LedgerView`：**172 µs → 1.8 µs**，
数字逐位不变。**不是**"克隆时把 `msgs` 丢掉"就完事 —— `add` 靠 `msgs` 去重，被掏空的账本再加
同一行就会把一次调用算两遍（本仓最恨的"安静地算错"），所以做成一个**没有 `add` 的只读类型**。
顺带删掉 `Ledger::session_tokens`（UI 改走视图后它成了生产代码里没人调用的第二把尺子）。

## 2026-09-18（再续）· 修"明明完成了却还是显示工作中" —— 根因是 `last_line_at` 被家务行推进

用户报："有时候明明完成了却还是显示工作中"。**这是我上一轮那个改动放大的**（把 `Idle`
放进活动覆盖），但**根因比它更老**。

### 一、取证（真机，探针逐列打印）

让生产代码在真机跑一遍，把每个会话的**状态文件、decay 结果、`last_line_at`、以及那条
覆盖的判据**全列出来。当时 5 个宿主还活着的会话：

| 会话 | 状态文件 | 挂件显示 | 距上次 Stop | 转录最后一行比它晚 |
|---|---|---|---|---|
| `02e4a8ec` | **done** | **工作中** ✗ | 39 分钟 | **186 秒** |
| `d5c66a37` | **done** | **工作中** ✗ | 12 分钟 | **182 秒** |
| `ec186506` | done | 完成 ✓ | 6 分钟 | 0 秒 |
| `975cc8cb` / `f3d21216` | working | 工作中 ✓ | —— | 434 / 390 秒（真在跑）|

看那两个 ✗ 的转录最后三行：**全是 `type=system`**（不是助手发言）。

### 二、根因

`parse_delta` 里 `last_line_at` 取的是**任何带时间戳的行**，不看行类型。而转录里混着一批
**家务行**：`system` / `file-history-snapshot` / `last-prompt` / `cost-state` / `attachment` /
`queue-operation` —— Claude Code 自己在做事，与"这个会话在不在干活"无关。于是 `Stop` 之后
三分钟落进三行 `system`，那条"转录动过 ⇒ 工作中"的覆盖就被签上了名。

**为什么这轮才暴露**：上一轮之前，覆盖只认 `Waiting | Done`，而 `Done` 会在 `idle_after_sec`
后被 `decay` 降级成 `Idle` ⇒ 覆盖**自动失效**，家务行最多让界面错 5 分钟；上一轮把 `Idle`
放进覆盖（为了修"被唤醒的回合显示待命"），降级不再能终止覆盖 ⇒ 家务行带来的误判变成**永久**。
**两个改动都要留**：只有对话行能推进活动时间（本轮），加上 `Idle` 也参与覆盖（上一轮）——
合起来的效果是"**真的有人在写对话**才算在干活，多老都算"。

### 三、改法与验证

只认对话行（`assistant` / `user`）推进 `last_line_at`。

| 项 | 结果 |
|---|---|
| 测试 | **246 + 2 = 248** → **247 + 2 = 249**（新增 `housekeeping_lines_do_not_count_as_activity`，夹具的三条时间戳**逐字取自真机那三行 `system`**）|
| 变异 | 把行类型限制去掉 ⇒ 新用例**红**（`left: 1789721256`（system 那行）/ `right: 1789719710`（assistant 那行））|
| 真机复核 | `02e4a8ec` / `d5c66a37` 从"工作中"变回**待命** ✓；`975cc8cb` / `f3d21216`（转录 11/13 秒前还在动）**仍是工作中** ✓ |

### 一、#2 分隔线颜色：钉成 `#BEBEBE`，并且**连画法一起换掉**

浅色主题 `gray(190)` = `#BEBEBE`、**深色主题 `gray(60)` = `#3C3C3C`**（画在纯白面板上反而更重）。
⇒ **同一个 exe 在两台机器上长得不一样**，而这是全项目唯一一处在跟着系统跑（面板底色、每个字、

那会让**同一个 `Ui` 上将来任何非交互控件**连带变色。改成**自己画**（`rule(ui)`，与 `paint_right` /
`draw_subagent_link` 同一个路子）：

```rust
let (rect, _) = ui.allocate_at_least(egui::vec2(ui.available_width(), 0.0), egui::Sense::hover());
ui.painter().hline(rect.left()..=rect.right(), rect.center().y,

```

⚠️ **高度必须是 `0.0`**：取 `RULE_WIDTH` 当高度会让游标多走 1pt、线也下沉 0.5pt，
四段纵向间距全线 +1（`EXTRA_ROW_GAP` 的 58 是**文字原点差**，量得出来）。

### 二、#4 计时器挤会名：先量清"多一位要多少 pt"，再改计时格式

原遗留只写了一句"计时到 `100:00` 多一位数，220 的承诺失效"。先把这条**量成一条线**：

| 计时 | 字符数 | 会名保持两个字所需的最窄窗宽 |
|---|---|---|
| `62:05` | 5 | 209 |
| `100:00` | 6 | **222** |
| `1000:00` | 7 | **234** |
| `10000:00` | 8 | 246 |
| `100000:00` | 9 | 258 |

**每多一个字符恰好 +12pt**（就是数码体一个数字的宽）。

⚠️ **我在这里报错过一次数，记下来**：第一版只采了 220 / 228 两个宽度就向用户报"补 8pt 到 228"
—— 细采之后真实门槛在 **221～221.5 之间**，取整是 **222**。**两点之间的东西全是猜的**，
这正是本仓"实测数字不保鲜"的老毛病，本次又踩了一遍。

更要紧的是：**这不是"要不要补 8pt"的问题，而是"补到哪儿算完"的问题** —— 计时是**无上界**的。
把它从推演变成事实的是真机：探针暴雷时抓到一行

```
▍f01 到 f15 文件顺…   已退出  8368:11
```

**一个开了 5.8 天的会话，右端写着 `8368:11`** —— 既长（把会名挤没）又根本读不懂（那是 139 小时 28 分）。

所以用户 2026-09-21 裁定**改计时格式本身**：**满 1 小时从 `MM:SS` 换成 `H:MM`**
（`8368:11` → `139:28`；秒在 `H:MM` 档不显示）。切换点选 **1 小时**而不是"MM:SS 撑到 99:59"，
因为切换那一瞬数字会往回跳：`59:59 → 1:00` 是时钟整点进位、谁都认得，`99:59 → 1:40` 则是
纯粹的数字倒流，看着像 bug —— **两个方案的长度收益完全一样**，所以选可读的那个。

两档合起来：`MM:SS` 恒 5 字符 → `H:MM` 到 100 小时（4.2 天）才 6 字符 → **1000 小时（41.7 天）才 7 字符**。
下限因此从 **220 调到 222**（按 6 字符档取），**覆盖到 41.7 天**。
📌 **上界只是被推远、没有被消灭** —— `the_timer_switches_to_hours_at_the_hour_mark` 的最后一格
`100000:00` 就是**故意钉住"它还会变长"**，免得有人读上面那张表以为 `H:MM` 恒为 5 个字符。

## 2026-09-23 · "凭空冒出来一个显示成本模块 estimate.rs 的会话"（僵尸状态文件 + pid 回收）

用户原话："现在老是弹出一个会话显示成本模块 estimate.rs 在 HUD 里，是什么情况。"
**不是新会话，也不是幻觉** —— 是 09-18 那次实验留下的**僵尸状态文件**，被 Windows 的
**pid 回收**复活到桌面上。

### 一、取证（探针复现，不是读代码想出来的）

先把"行从哪来"这条链走死：`view::build_rows` 的入参只有 `state::list_all(sessions_dir)`
—— **界面上每一行都必然对应 `%APPDATA%\claude-hud\sessions` 里的一份 JSON**。挂件侧当时
抓到的两帧都只有 3 行，且与 3 个活着的 `claude.exe` 一一对应（含用户此刻这个会话，
标题 `HUD 中 estimate.rs 成本模块弹出` —— 那是 Claude Code 自己按用户提问生成的 aiTitle）。

于是拿**真数据**做探针（独立目录 + 独立配置起第二个挂件实例，跑完即杀，全程没碰真目录）：

| 做法 | 结果 |
|---|---|
| 复制真状态目录，把僵尸文件 `49f8a161`（标题 `estimate.rs 成本模块加 Ledger 以及 Tally`，原 pid 32072）的 `claude_pid` 改成**此刻活着的** pid | 启动 **1.2 s**：15 行，第一行就是它；**6 s**（暖机收敛后）：**它还在，还排在最前** |

**破绽写在脸上**：状态 `待命`、计时 `125:35` —— 那是 **09-18** 的陈旧值（距今 5 天）。
证据图：`%TEMP%\hudwatch\evidence\probe_01.png` / `probe_02.png`。

pid 回收不是假设，是本机事实：**09-15 那个会话记的 pid `19864`，现在被 VS Code 占着**。
用户盘上 19 份状态文件里 **15 份是僵尸**，其中 4 份标题正是 `estimate.rs 成本模块…`
（`32072 / 12352 / 30560 / 28676`）—— 下一个领到这些号的 `claude.exe` 就会让它"凭空出现"，
领到的是别的程序（像 VS Code 那样）就继续藏着 ⇒ **时有时无，正是用户说的"老是弹出"**。

### 二、根因是两半，缺一不可

| 半 | 现状 |
|---|---|
| 僵尸**没人删** | 挂件按 Ruling #6 **不写**状态文件（删也是写），hook 侧也没有清扫 ⇒ 文件只增不减 |
| 存活判据**只认 pid 一位数** | `procinfo::alive` = "pid 打得开 + 映像名是 `claude.exe`"。回收的号落到**任何一个新的 `claude.exe`** 头上就成立 |

### 三、改法（两条一起上）

1. **身份**：状态文件新增 `claude_start`（宿主的 Win32 `FILETIME` 创建时间），hook 在
   `SessionStart` 抓 pid 时**同一个句柄**顺手取（微秒级）。存活判定改成"pid + 映像名 +
   创建时间**精确相等**"。老文件没有这个字段 ⇒ 退回老判据（**宁可漏报僵尸，不可误杀活人**）。
   ⚠️ 写盘时 `claude_pid` 与 `claude_start` **必须整组换**（`hook::merge_host`）：一个 pid 配
   另一个进程的创建时间，会把**活着的**会话判死 —— 那是这套机制唯一的伤人方向，已单独钉测试。
2. **清扫**：`SessionStart` 上删掉"**确认已死**且静默超过 1 小时"的状态文件。由 hook 做
   （它本来就是这些文件唯一的写者，Ruling #6 一条都不用破）。宽限期是保守值：挂件自己
   两轮（约 2 s）就把死行撤掉，清扫不抢那几秒。

### 四、验证

| 项 | 结果 |
|---|---|
| 测试 | **251 + 2 = 253** → **259 + 2 = 261**（+8：身份 1 · 挂件接线 1 · 清扫 4 · 写盘/续宿主 2）|
| 变异 | **9 次全红**：身份判据失效（红 3）· 老文件一律判死（红 6）· 挂件没把创建时间交下去（红 1）· 清扫跑到每个事件（红 1）· 去掉宽限期（红 1）· 没 pid 的也当僵尸删（红 1）· 抓不到时只清创建时间（红 3）· 创建时间没写盘（红 2）· 写盘用旧创建时间（红 2）|
| 编译警告 | 仍 **5 条**（与改前一一对应，没加 `#[allow]`）|
| 真数据·干跑 | 拿**真状态目录的副本**跑新 hook 的 `SessionStart`：**19 份 → 4 份**（3 个活会话 + 探针新建的那份），**15 份僵尸全清、活的没动一份** |

### 五、两条踩坑账（都值得下次先读）

1. **我自己的干跑第一次全空**：命令串过了一层 shell，`\` 被吃成 `\`，JSON 里成了 `"D:\w"`
   —— 非法转义 ⇒ `HookPayload::parse` 失败 ⇒ hook **静默 `exit 0`**。表现是"什么都没发生"，
   与"清扫没生效"长得一模一样。**hook 的静默设计是对的（绝不能阻塞 Claude Code），
   所以干跑时必须先自证"这一步真的跑到了"**（本次靠换成不含反斜杠的 cwd 才分开）。
2. **变异脚本用 `shutil.move` 还原后 cargo 不重编**（mtime 倒退）—— 9 次变异跑完，回归
   却报 2 条红，看着像新代码坏了。`touch src/*.rs` 后立刻全绿。**这条坑 2026-09-20 记过一次
   （变异取证后 mv 还原须 touch），这次是在 Python 脚本里又踩了一遍。**
