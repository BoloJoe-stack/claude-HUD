# claude-hud · dsh 桥接方案

> 目标：让挂件同时显示 Claude Code 会话与 DeepSeek Harness（下称 dsh）会话。
>
> 状态：**Phase 1 已交付，真机验收通过** · Phase 2 未开工 · 最后更新 2026-11-24
>
> 前置研究：`临时文件\hud-dsh-probe\`（asar 抽取的官方文档、dsh 转录探针脚本、实测数据）

---

## 1. 结论

采用「**一个产品、两段代码**」：

1. **dsh 桥接插件**（JS）运行在 dsh 宿主进程内，订阅会话事件，把事件翻译为状态文件。
2. **claude-hud**（Rust）保持只读消费者，读取状态文件并渲染，不感知 dsh 的存在。
3. 两段代码同仓库、同版本号、同一次发布；桥接由 HUD 安装与卸载，用户不单独维护。
4. 状态文件与 Claude Code 共用 `%APPDATA%\claude-hud\sessions\`，以 `provider` 字段区分来源。

该结构与现有的 hook 机制同构：Claude Code 用 8 个 hook 写状态文件，dsh 用 1 个插件写同样格式的状态文件。挂件的读取、排序、渲染、存活回收逻辑全部复用。

## 2. 问题与约束

### 2.1 现状

挂件的唯一数据源是 8 个 Claude Code hook 写入的 `%APPDATA%\claude-hud\sessions\*.json`；程序不扫描进程、不扫描其他工具（README「会话数的来源」）。因此同时运行 dsh 时，挂件不显示任何 dsh 会话。

### 2.2 dsh 侧的硬约束（已验证）

| 约束 | 证据 |
|---|---|
| 无进程外事件接口 | 无 hook 配置体系；`known-event-types.js` 中的 `hook/*` 是 agent 内部钩子，不是用户脚本 |
| 会话与进程无一一对应 | Electron 应用，实测 5 个 `DeepSeek Harness` 进程（1 主进程 + GPU/网络/renderer 子进程）；会话缓存中无任何 pid 字段 |
| 私有格式会随版本变化 | 转录为 `session.v4.jsonl.zstd`（多帧 zstd）；投影缓存为 `version: 7`；应用走 nightly 更新渠道 |
| 插件 API 可用且有文档 | `app.asar` 内含 `dsh/docs/cordis-tutorial/01-first-plugin.zh.md`；`dsh-session` 与 `dsh-agent` 均带中英文 README |
| 第三方插件已在使用同一扩展点 | 本机 `dsh-aurabot-qq` v1.2.1 以 `ctx.on('session/event', (session, event) => …)` 订阅事件并处理 `approval/asked` |
| 插件支持本地绝对路径安装 | `dsh-plugin-manager/lib/types/install-spec.js`：`kind: 'path'`，要求绝对路径 |

### 2.3 目标

1. dsh 会话与 Claude 会话同屏显示，状态语义一致。
2. 用户只需要运行一个程序：`claude-hud.exe`。
3. 桥接失效时，界面明确说明「dsh 数据不可用」，不得静默显示 0 行。

## 3. 架构

```
┌─────────────────────────┐        ┌──────────────────────────────┐
│ Claude Code 会话         │        │ DeepSeek Harness（Electron）  │
│ 8 个 hook                │        │  dsh-hud-bridge 插件          │
└───────────┬─────────────┘        └──────────────┬───────────────┘
            │ 写 JSON                              │ 写 JSON + 心跳
            ▼                                      ▼
   %APPDATA%\claude-hud\sessions\<id>.json   %APPDATA%\claude-hud\dsh-bridge.json
            │                                      │
            └──────────────┬───────────────────────┘
                           ▼
                  claude-hud.exe（只读消费者）
```

### 3.1 职责划分

| 组件 | 职责 | 不负责 |
|---|---|---|
| dsh 桥接插件 | 订阅事件、维护状态、写状态文件与心跳、清理已结束会话的文件 | 渲染、聚合、存活判定 |
| claude-hud | 读取、排序、渲染、按心跳判定 dsh 存活、安装/卸载桥接 | 解析 dsh 私有格式、理解 dsh 事件 |

### 3.2 为什么不在 HUD 内轮询 dsh 文件

投影缓存实测滞后：10:08:54 缓存仍停在 `seq=438`，而转录已写到 10:12:53（约 4 分钟）。准实时需解码多帧 zstd 并适配私有 schema，耦合面大于插件方案。轮询仅作为**桥接不可用时的降级选项**保留在讨论范围外，不在本方案内实施。

## 4. 接口契约

契约由 HUD 定义，桥接负责实现。契约版本号 `contract: 1`。

### 4.1 状态文件

路径：`%APPDATA%\claude-hud\sessions\<session_id>.json`
与 Claude Code 共用目录。Claude 侧 `session_id` 为 UUID，dsh 侧为 `session-<uuid>`，无碰撞。

```json
{
  "session_id": "session-1d5095ac-6acf-47b6-8116-9c52d2531a3f",
  "cwd": "D:\\dsh_workspace",
  "display_name": "鲸鱼娘B站QQ插件配置",
  "provider": "dsh",
  "state": "working",
  "state_since": 1795486129,
  "last_event": "turn/start",
  "last_event_at": 1795486129,
  "nested": false,
  "context_tokens": 302702,
  "context_limit": 1000000,
  "transcript_path": null,
  "claude_pid": null,
  "claude_start": null,
  "last_assistant_message": null,
  "notification_message": null,
  "transcript_offset": 0
}
```

| 字段 | 来源 | 说明 |
|---|---|---|
| `session_id` | `session.id` | 必需 |
| `cwd` | `session.header.cwd` | 必需；HUD 用末段作兜底名 |
| `display_name` | `session/title` 事件 | 无标题时留空，HUD 回落为文件夹名 |
| `provider` | 常量 `"dsh"` | 新增；缺失视为 `claude`，兼容旧文件 |
| `state` | 事件映射（§4.3） | 取值集合与 Claude 侧一致 |
| `state_since` | 状态变更时刻 | 仅在状态值变化时更新 |
| `last_event` / `last_event_at` | 最新事件 | 用于计时与诊断 |
| `nested` | `session.header.origin == "subagent"` | HUD 已有过滤：`Some(true)` 不列 |
| `context_tokens` | 最近 `assistant/message.data.usage` | `inputTokens + cacheReadTokens + cacheWriteTokens` |
| `context_limit` | `request/context.data.contextWindow` | 实测 deepseek-v4.1-flash 为 1,000,000 |
| `claude_pid` / `claude_start` | 恒为 `null` | 不得写入 dsh 进程 pid；HUD 的 pid 存活判据不适用于 dsh |

### 4.2 心跳文件

路径：`%APPDATA%\claude-hud\dsh-bridge.json`（**不得**放入 `sessions\`，否则会被当作会话文件扫描）

```json
{
  "contract": 1,
  "version": "1.1.0",
  "pid": 23252,
  "heartbeat_at": 1795486129,
  "sessions": 3
}
```

| 规则 | 值 |
|---|---|
| 写入周期 | 15 秒 |
| 判定过期 | HUD 侧 `now - heartbeat_at > 90` 秒（允许连续丢失 6 次） |
| 文件缺失且存在 `provider=dsh` 的行 | 视为桥接不可用，全部标记「已退出」 |
| 版本不匹配 | `contract` 不等于 HUD 支持的版本时，HUD 在 `--doctor` 与界面提示「桥接版本不兼容」 |

### 4.3 事件到状态的映射

| dsh 事件 | HUD 状态 | 备注 |
|---|---|---|
| `session/created` （新建或恢复） | `idle` | 写文件 |
| `turn/start` | `working` | |
| `step/start` / `step/end` / `tool/call` / `tool/result` | 保持 `working` | 不改变状态，仅更新 `last_event` |
| `approval/asked` | `waiting` | 记录 `data.id` 到待审批集合 |
| `approval/decided` | `working` | 从集合移除同一 `id`；`turn/end` 时清空该会话全部待审批项 |
| `compaction/start` | `compacting` | |
| `compaction/end` | `working` | |
| `turn/end`，`reason.kind == "completed"` | `done` | |
| `turn/end`，`reason.kind == "interrupted"` | `interrupted` | |
| `turn/end`，其他 `reason.kind` | `error` | |
| `session/disposed` | —— | 删除该会话的状态文件 |
| `session/title` | 不改变状态 | 更新 `display_name` |
| `assistant/message` | 不改变状态 | 更新 `context_tokens` 与 `last_assistant_message` |
| `request/context` | 不改变状态 | 更新 `context_limit` |
| `job/registered` / `job/settled` | 不改变状态 | Phase 2 可选：输出后台任务数 |
| 未知事件 | 不改变状态 | 前向兼容 |

### 4.4 会话可见性

| 情形 | 处理 |
|---|---|
| 子代理会话（`origin == "subagent"`） | 写 `nested: true`，由 HUD 现有规则隐藏 |
| 历史会话（不在 `ctx.sessions.list()` 中） | 不显示；口径与 Claude 侧「hook 之后打开的会话才可见」一致 |
| 仅 headless / CLI 启动的 dsh | 不覆盖；桥接只在桌面应用进程内运行 |
| dsh 被强制结束 | 心跳过期，HUD 标记全部 dsh 行「已退出」，两轮后移除 |

### 4.5 启动时的状态种子

插件加载时枚举 `ctx.sessions.list()`，对每个存活会话写 `state: "idle"`，由下一条事件纠正。

已知限制：插件安装或 dsh 重启时正处于「工作中 / 等待确认」的会话，在产生下一条事件前会显示为待命。原因是插件只依赖注入的 `ctx` 与事件流，不 import `@deepseek-ai/*` 包、不读私有缓存。该限制写入 README。

## 5. dsh 桥接插件

### 5.1 包结构

```
dsh-bridge/
  package.json          # name: dsh-hud-bridge, private: true, type: module
  cordis.patch.yml      # insert: [{ id: hud-bridge, name: dsh-hud-bridge }]
  src/host.js           # 唯一运行时文件
  test/mapping.test.js  # node --test
  README.md
```

不引入构建步骤；运行时代码为纯 JS，Node 版本要求与 dsh 一致（>= 22.13）。

### 5.2 入口

```js
export const name = 'hud-bridge'
export const inject = ['sessions', 'timer']
export function apply(ctx) { … }
```

约束：

1. 只使用 `ctx` 注入的服务与事件，**不 import 任何 `@deepseek-ai/*` 包**。第三方插件的现状是仅用 `ctx`；避免依赖应用内部模块解析。
2. 所有回调包在 `try/catch` 中，任何异常只写日志，不向外抛出，避免影响 dsh 主进程。
3. 不注册 UI、不监听端口、不发网络请求。

### 5.3 写入策略

| 项 | 规则 |
|---|---|
| 原子写 | 先写 `<id>.json.<pid>.tmp` 再 `rename`，与 HUD 状态文件同一约定 |
| 防抖 | 每个会话最多每 200 ms 落盘一次；心跳单独 15 秒一次 |
| 路径 | 由 `process.env.APPDATA` 推导；取不到时写日志并停用 |
| 文件清理 | `session/disposed` 删除；插件卸载时删除全部 `provider=dsh` 的状态文件与心跳 |
| 日志 | `%APPDATA%\claude-hud\dsh-bridge.log`，单文件上限 256 KB，超限轮转一次 |

### 5.4 安装

dsh 官方支持绝对路径安装。HUD 执行以下步骤（幂等）：

1. 检测 `<用户目录>\.dsh\profiles\desktop\package.json` 是否存在。不存在则判定未安装 dsh，不提示。
2. 将 `package.json`、`cordis.patch.yml`、`src/host.js` 复制到
   `%APPDATA%\claude-hud\dsh-bridge\`。
3. 将同一组文件复制到 `<profile>\node_modules\dsh-hud-bridge\`，使包名可被解析。
4. 修改 profile 的 `package.json`：
   - `dependencies["dsh-hud-bridge"] = "link:<第 2 步目录>"`
   - `dsh.profile.bundles` 追加 `"dsh-hud-bridge"`（已存在则跳过）
   - 修改前备份为 `package.json.claude-hud.bak`
5. 提示「重启 DeepSeek Harness 后生效」。

失败处理：profile 的 `package.json` 无法解析时，报错原文并**不做任何修改**，不覆盖用户配置。

降级路径：若第 3、4 步被 dsh 后续版本破坏，提示用户用 dsh 设置 → 插件 → 输入第 2 步目录的绝对路径安装（官方支持的 `kind: 'path'` 路径）。

### 5.5 卸载

移除 `bundles` 条目与 `dependencies` 项、删除 `node_modules\dsh-hud-bridge\`、删除桥接目录、删除全部 `provider=dsh` 的状态文件与心跳文件。不改动 profile 中其他插件。

## 6. claude-hud 侧改动

| 文件 | 改动 | 测试 |
|---|---|---|
| `src/state.rs` | `SessionState` 增加 `provider`、`context_tokens`、`context_limit`（均 `#[serde(default)]`） | 旧文件兼容：缺新字段仍可解析，且读成 `None` |
| `src/ui.rs` | `poll_once` 读心跳；心跳过期或缺失时，把 `provider=dsh` 的行并入 `gone` 集合 | 89/90/91 秒边界；心跳文件缺失；无 dsh 行时零开销 |
| `src/view.rs` | `context_pct` 优先取会话自带 `context_tokens / context_limit`，缺失时回落到现有 Delta + 全局配置 | 两条来源各一例；上限为 0 时不出百分比 |
| `src/ui.rs` | 顶栏计数：仅 Claude 时保持 `● claude 会话 · N 个` 原文；存在 dsh 行时改为 `● 会话 · N 个（claude A · dsh B）` | 两种文案各一条断言 |
| `src/ui.rs` | 每行加工具标识（dsh 行显示 `dsh` 小标签）；不改变行高与列宽布局 | 行高不变、最窄宽度余量不变 |
| `src/dsh_bridge.rs`（新增） | 检测、安装、卸载、状态查询，结构参照 `hooks_install.rs` | 临时 profile 夹具：安装幂等、备份生成、坏 JSON 不修改 |
| `src/main.rs` | 首次运行增加第三问：「检测到 DeepSeek Harness，是否显示它的会话」；新增 `--install-dsh-bridge` / `--uninstall-dsh-bridge` | 首次运行只问一次；命令幂等 |
| `src/doctor.rs` | 增加桥接检查：文件存在、`contract` 版本、心跳距今秒数 | 三种状态各一条 |

不修改 `procinfo` 与 `state` 的既有存活判据；dsh 的存活完全由心跳承担。

## 7. 打包与版本

1. 桥接源码位于仓库 `dsh-bridge/`，不进入 Rust 构建的依赖图。
2. 三个运行时文件以 `include_bytes!` 嵌入 exe；安装时解出。发布物仍为单个 exe + zip。
3. 版本号只在 `Cargo.toml` 维护；`build.rs` 不存在，桥接版本通过 `env!("CARGO_PKG_VERSION")` 写入 `package.json` 与心跳。
4. `dsh-bridge/package.json` 的 `version` 在构建时由构建脚本替换，或在安装时由 HUD 重写。**采用后者**，避免引入构建脚本。
5. 桥接不单独发布到 npm；仓库公开时随源码公开（MIT）。

## 8. 分阶段实施

### Phase 1：桥接先行（HUD 不改）

交付：`dsh-bridge/` 全部源码、单测、README、手工安装说明。

验收：

| # | 场景 | 预期 |
|---|---|---|
| 1 | 安装桥接并重启 dsh | `%APPDATA%\claude-hud\dsh-bridge.json` 在 60 秒内出现 |
| 2 | 在 dsh 发起一轮对话 | 挂件在 2 秒内出现该行并显示「工作中」 |
| 3 | 触发需要授权的工具 | 显示「等待确认」；批准后回到「工作中」 |
| 4 | 回合结束 | 显示「完成」 |
| 5 | 关闭 dsh | 心跳停止；Phase 1 无 HUD 侧判定，行保留至挂件重启。该行为在 Phase 2 修正 |

已知限制：无存活判定；上下文占比按 HUD 全局上限计算，dsh 上限为 1M，可能与用户配置不一致。

### Phase 2：HUD 接入

交付：§6 全部改动、`--install-dsh-bridge` / `--uninstall-dsh-bridge`、首次运行询问、`--doctor` 检查、测试。

验收：

| # | 场景 | 预期 |
|---|---|---|
| 1 | 1 个 Claude 会话 + 2 个 dsh 会话 | 挂件 3 行；顶栏为 `● 会话 · 3 个（claude 1 · dsh 2）` |
| 2 | 仅 Claude 会话 | 顶栏与当前版本逐字一致 |
| 3 | 关闭 dsh | 90 秒内 dsh 行标记「已退出」，两轮后移除；Claude 行不受影响 |
| 4 | 强制结束 dsh 进程 | 同上 |
| 5 | dsh 升级后插件失效 | `--doctor` 报告心跳过期；界面明确显示桥接不可用，不显示 0 行的假象 |
| 6 | 卸载桥接 | dsh 行与状态文件全部消失；Claude 行不受影响 |
| 7 | 上下文占比 | dsh 行按 1,000,000 计算；Claude 行仍按用户配置 |

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| dsh nightly 更新改动插件 API 或事件名 | 桥接停止写状态 | 只订阅 5 类核心事件；全部 `try/catch`；心跳过期由 HUD 明确报不可用；日志留证 |
| 插件异常影响 dsh 主进程 | 影响用户主要工具 | 纯监听、不阻塞、不抛异常、写盘防抖 |
| 直接改 profile 的 `package.json` 与 pnpm 冲突 | 安装失败或被下次 pnpm install 覆盖 | 安装前备份；幂等可重装；失败时降级为 dsh 官方插件界面按路径安装 |
| 同一目录混放两类状态文件 | 误判或文件名碰撞 | dsh id 带 `session-` 前缀；`provider` 字段缺省为 claude；桥接只删除自己写入的文件 |
| 会话在插件加载前已处于工作中 | 暂时显示待命 | 接受该限制并写入 README；不引入对私有格式的依赖 |
| 桥接版本与 HUD 版本漂移 | 字段语义不一致 | `contract` 版本号；不匹配时 HUD 明示 |

### 13.3 本次新增的实证结论

1. **`request/context` 是低频事件**。它在会话第一次请求（或模型变化）时发一次，后续回合
   只发 `request/header`。因此 `context_limit` 只对「插件加载后新建的会话」可靠，
   恢复的老会话拿不到；Phase 2 必须保留「缺失 ⇒ 回落全局配置」的分支，不要给默认值。
2. **`session/title` 同理**：标题事件发生在插件加载前的会话不会被重放 ⇒ 显示文件夹名。
   该限制已写入桥接 README（比原 §4.5 的范围更宽）。
3. **绝对路径 `insert` 可用**：`--patch` 覆盖层里写
   `name: <仓库>/dsh-bridge/src/host.js` 即可让 cordis 直接加载该模块，无需改
   profile 的 `package.json` / `node_modules`。沙箱验证（headless profile）就是这么做
   的；Phase 2 的降级路径可以再快一档。
4. **desktop profile 被应用独占**：`dsh --profile desktop --dump-config` 直接报
   `profile "desktop" is managed exclusively by the Electron application`，CLI 无法
   预检桌面 profile 的合成结果 —— 桌面侧只能靠重启验证。
5. **profile 变更会被热加载**：安装桥接后、重启之前，日志里已经出现「桥接已启动」，
   说明 cordis loader 监视 profile 文件。Phase 2 的「重启后生效」提示可以放宽为
   「通常无需重启」，但验收仍以冷启动为准。
